# 主题式源码研读（v2）

给定一个主题 + 一个或几个项目 → 把相关代码全部切出来 → 产出讲设计取舍的文章，或可并入 skill 的规则。

相对 v1 的变化：增加多项目对比模式、skill 规则产出模式；修正浅克隆导致看不到提交历史的问题；增加 PR / issue 作为 why 的来源；点名最值钱的研究目标；增加成本控制；增加「先文章、经用户确认、再规则」的确认闸门和文末核验清单；多项目模式改为「广度定位 + 关键机制深挖」两段，深挖用机制卡讲到参数级、静默失败和踩坑；交付前做结论自检；参数表的调整方向必须标依据；长文交付前做去重压缩。

## 三条必须先知道的事

**第一：常规的代码搜索策略是为「改代码」优化的，和本 skill 目标相反。**

改代码时的正确做法是：找到够改的那几处就停，不做传递扩展，尽快动手。
**研究性阅读恰恰相反：要的是完整覆盖，必须传递扩展，宁可多切不可漏切。**

不要因为「已经能回答问题了」就停。停止条件写在第 4 步，只能用那三条。

**第二：读代码的方式和写成品的方式是两回事。**

第 1-5 步（找代码）你要看行号、看符号、看调用链。
**第 6 步学习者档文章默认一个行号都不出现。**
把研读过程的中间产物当成成稿交出去，是这类产出最常见的失败。

**第三：一个项目的选择不等于通用最优。**

只读一个项目时，产出里只能说「这个项目这样做」，不能写成「应该这样做」。
要得出可以写成规则的结论，至少对比 2 个项目（见「多项目对比」）。

## 第 0 步：备料

### 定三件事（不准跳）

| 问题 | 选项 | 默认 |
|---|---|---|
| **读者** | 学习者 / 开发者 | 学习者 |
| **项目数** | 单项目 / 多项目对比（2–3 个） | 用户给几个算几个 |
| **产出** | 文章 / skill 规则 / 两者 | 文章；目标是并入某个 skill 时默认「两者」 |

读者档位：

| 档 | 读者读完要干什么 | 第 6 步走哪套 |
|---|---|---|
| **学习者**（默认） | 看懂这个设计，能讲给别人听，能用到自己的东西里 | 正文无行号、无代码块 |
| **开发者** | 照着文章去翻代码、改代码 | 可带行号与切片清单 |

**判断不准时默认学习者档。** 学习者档的文章开发者也读得下去；反过来不成立。

用户说「整理给 skill 用」「沉淀成规则」「并入 XX skill」时，产出默认选「两者」，并走下面的确认闸门；用户明确说「只要规则、不用文章」才只走 6B。

**「两者」的顺序（确认闸门，不准跳）：**

1. 先只走 6A，交付文章（含文末核验清单），然后停下，请用户核验。
2. 用户核验后，按反馈修订文章，得到「确认版」。用户指出的错误、删掉的结论，一律不进入规则。
3. 再走 6B，**只从确认版文章里提炼规则**，每条规则注明出自文章哪一节。文章里没有的结论，不准在规则里新增。
4. 规则清单交给用户审，用户同意后才合入目标 skill。

理由：用户的核验是这类产出可信度的主要来源。规则如果绕过文章直接产出，用户就要在更短、更抽象的规则上做核验，错误更难发现。

用户只给一个项目却要 skill 规则时，提醒一句：单项目只能产出「参考做法」，建议再加 1–2 个同类项目；用户坚持就照做，并按单项目规则标注。

### 拿代码

**要保留提交历史**，否则第 3 步的 git log 和 blame 都用不了。用「无文件内容克隆」：历史完整，文件内容按需下载，体积接近浅克隆：

```bash
git clone --filter=blob:none <repo-url> /home/claude/study/<name>
```

- 网络受限或仓库极大时才用 `--depth 1`，并在覆盖说明里写明「未读提交历史」。之后需要历史可以 `git fetch --unshallow`
- 克隆后先报一下规模（文件数、主要语言、顶层目录、提交数、最近一次提交日期），让用户心里有数
- **记下快照**：提交哈希 + 日期，写进覆盖说明

**用户本地已经有一份时**：以**本地那份为准**。可以另克隆一份用来快速搜索，
但先比对几个文件的大小确认版本是否一致。**版本不一致就在文末标明快照日期。**

### 拿不到代码时

闭源产品：**直说拿不到**，改成分析现有材料（官方开源的 SDK / 规范、工程博客、公开文档、同类开源项目），
并在产出里标明「本文基于 XX 材料，未读到实现代码」。**不要假装在读代码。**

**不主动寻找或使用未经授权的泄露源码。** 用户自己提供泄露材料时，提醒一句：这是未授权内容，在公司内使用有合规风险，建议改用官方公开材料；用户坚持则必须在产出中标清来源、版本，并说明不是官方发布、可能已过时。

### 定产出存放位置

用户连接了本地文件夹时，产出统一存到用户指定的研读目录（未指定就问一次，例如「my skills/研读」），命名：`主题-项目-YYYYMMDD-文章.md`、`主题-项目-YYYYMMDD-规则.md`；文章修订后覆盖同名文件，并在文末记修订日期。没有连接文件夹时，作为文件交付到对话里。

### 定主题边界

把用户的主题复述成一句话，并明确写出**不算在内的**：

> 「本次研究：上下文超长时怎么压缩。
>  不包括：模型选型、提示词拼装、流式输出。对吗？」

边界不定，扩展阶段会失控。多项目模式下，所有项目共用同一个边界。

### 定项目定位（多项目模式必做，单项目也建议做）

每个项目用一行写清：

> 项目名 @ 快照日期 | 类型（运行时内核 / 框架 / CLI 产品 / 业务应用） | 主要场景 | 规模

定位不同的项目，做法不同很正常，不能直接比优劣。这一行要进最终产出。

### 定深度预算（多项目模式必做）

多项目研读分两段，不平均用力：

| 段 | 精力占比 | 做什么 | 产出 |
|---|---|---|---|
| **广度段** | 约 40% | 每个项目各自走第 1–5 步，再做对比矩阵 | 摸清每个项目在各维度上怎么做，找出候选深挖点 |
| **深挖段** | 约 60% | 对选中的 2–4 个关键机制，跨项目读透 | 每个机制一张机制卡（见「深挖」一节） |

平均用力的后果：每个机制都只讲到「怎么做」，讲不到「参数为什么是这个量级、往哪边调会怎样、哪里出错不报错」，产出的规则偏少、偏「看条件」，读者拿不走能照做的东西。

深挖点在广度段结束后才选，选法见「深挖」一节；**选出后先给用户确认一次**，再开始深挖。

## 第 1 步：词表展开（不要跳）

**直接拿中文主题去 grep 是这件事最常见的失败方式。**
代码里不会写「上下文压缩」，只会写 `compact`、`truncate`、`prune`。

先把主题展开成**候选标识符词表**，五个来源：

| 来源 | 例（主题：上下文压缩） |
|---|---|
| **直译与同义词** | compact, compress, summarize, condense |
| **相邻动作** | truncate, trim, prune, evict, drop, discard |
| **度量与阈值** | token_budget, max_tokens, window, limit, threshold, usage |
| **缩写与惯用名** | ctx, msg, hist, buf, mem |
| **反向线索** | overflow, exceed, too_long, out_of_context |

另加两类容易被忽略但命中率很高的：

- **配置项名**（在 `*.toml` / `*.yaml` / `*.json` / `.env.example` 里搜）
- **日志与错误文案**（搜 `"context"`、`"too long"` 这类字符串字面量）

把词表列出来给用户看一眼（不用等确认），**后面每轮扩展都要回来补充这张表**——
读到新的同义词就加进去，这是第 4 步停止判据之一。

**多项目模式：** 共用一张基础词表，但每个项目各自补充——不同项目给同一件事起的名字不一样。

**一个重要提醒：「搜不到」本身就是发现。**
比如搜 `maxTurns` 零命中，说明这个项目根本不用轮数上限——这往往比找到一堆代码更有价值。

## 第 2 步：定种子

### 先看地形，再搜

1. 目录树限深度 3 层，排掉 `node_modules`/`vendor`/`target`/`dist`/`.git`
2. 读 `README`、`docs/`、`CHANGELOG`，以及 `rfcs/`、`adr/`、`design/` 这类设计文档目录里跟主题相关的部分——**作者自述是意图的一手证据**
3. 看有没有名字直接命中的文件或目录

### 搜索规则

- **单个标识符用 `rg` 精确匹配**，不要拿整句话去模糊搜
- **一次只找一件事**。「压缩怎么触发的」和「压缩怎么实现的」是两次搜索
- **并行跑**，不要一个词一个词串行
- 命中太多（上百处）的词要么加限定，要么丢掉——`limit` 这种词全仓都是

得到的是**种子符号**：几个函数名 / 类名 / 文件。这只是起点，不是答案。

## 第 3 步：传递扩展（核心一步）

从每个种子出发，**五个方向都要追**，一个都不能省：

| 方向 | 怎么追 | 能看到什么 |
|---|---|---|
| **向上：谁调用它** | `rg "\b<符号名>\b"` | 触发时机、入口 |
| **向下：它调用谁** | 读函数体 | 实现分解 |
| **类型与数据结构** | 搜参数和返回值的类型定义 | 状态怎么存的 |
| **配置与默认值** | 搜常量名、配置项、环境变量 | **默认值最能看出作者的假设** |
| **测试** | 搜测试目录里提到这些符号的 | **测试是可执行的规格说明**，能反推出边界条件 |

每轮扩展产生的新符号，**重新进入本步再跑一遍**。这就是传递扩展，不要在第一层就停。

### 重点挖这四类（最值钱）

| 目标 | 怎么找 | 为什么值钱 |
|---|---|---|
| **防御性代码** | 看起来多余的检查、预占、重试、兜底、上限；`git blame` 这几行，看是哪次提交加的 | 背后常是线上真出过的事故 |
| **刻意不做的事** | 搜 `not supported`、`intentionally`、`deliberately`、`won't`、`unsupported`、`out of scope`；读文档的 FAQ / 限制章节；看被关闭的 feature request | 这是作者的边界判断 |
| **默认值** | 常量、配置默认值；查它们的改动历史 | 数字不重要，重要的是为什么是这个量级、往哪边调会出什么问题 |
| **被撤回的设计** | `git log --grep=revert -i`；改动频繁的文件 | 设计反复横跳的地方，就是取舍最难的地方 |

「防御性代码背后是事故」是假设，不是结论。找到对应的提交 / PR / issue 才算证实；找不到就标「推断」。

### why 的一手证据：提交历史、PR、issue

**提交历史：**

```bash
git log --follow --format='%h %ad %s' --date=short -- <文件>   # 文件改动史
git log -S '<常量名或关键字符串>' --format='%h %ad %s'          # 某个值是哪次引入或改掉的
git blame -L <起>,<止> <文件>                                    # 某几行是哪次加的
```

commit message 里常直接写了为什么改。

**PR 与 issue（GitHub 项目）：** 事故经过和当时的取舍，很多写在 PR 讨论里，而不在 commit message 里。

```bash
gh api repos/<owner>/<repo>/commits/<sha>/pulls --jq '.[].number'   # 由提交找 PR
gh pr view <号> -R <owner>/<repo> --comments                          # 读 PR 描述与讨论
gh issue list -R <owner>/<repo> --state all --search '<关键词>' --limit 20
gh issue view <号> -R <owner>/<repo> --comments
```

squash 合并的提交标题里常带 `(#123)`，可以直接拿号去查。
只追关键设计点（防御性代码、默认值改动、撤回）的 PR，不要每个提交都查——会撞 API 频率限制，也浪费时间。

### 静默失败的线索（出错不报错的地方）

这类地方最值得写进产出，因为使用者自己最难发现。三类线索：

- **被吞掉的异常**：catch 之后只打日志、返回空、返回默认值
- **默认值兜底**：取不到配置或数据就用默认值，不告警
- **提交说明和问题单里的字眼**：`silently`、`without error`、`no error`、`unexpectedly`、`swallow`、「看起来正常但结果不对」

### 踩坑来源（补源码给不了的使用经验）

源码只给作者的设计选择，给不出使用者踩过的坑。用这三类材料补：

- **bug 类问题单**：按主题词搜 issue，优先看带 bug 标签、讨论多的，记下「现象 → 原因 → 怎么修的」
- **修复与回滚提交**：`git log --grep='fix\|revert' -i -- <相关路径>`，看哪些地方反复修
- **用户抱怨与讨论**：issue 和讨论区里「为什么 X 不生效」「升级后 Y 变了」这类

没有 GitHub 接口时用网页查看，按关键设计点限量查。

### 其他线索

- **注释里的 TODO / FIXME / HACK / NOTE / XXX**，作者在那里承认了妥协

## 第 4 步：什么时候停

**不准用「已经能回答问题了」作为停止理由。** 只能用这三条覆盖信号：

1. **新一轮扩展没有引入新文件**
2. **词表里的词已全部搜过，且读代码时没再发现新的同义词**
3. **每个入口点的直接调用方都已归类**（要么切进来了，要么明确判为无关）

三条都满足才停。跑到第 5 轮还不收敛，停下来告诉用户主题可能定得太大，建议拆。

**诚实声明：这三条是覆盖信号，不是覆盖证明。**
它们工程上够用，但不保证没有漏。产出末尾要写清楚本次覆盖到什么程度。

### 成本控制

- 仓库超过约 5000 个源文件，或单项目扩展到第 3 轮切片仍超过 60 条：先停下报告规模，建议缩小主题或限定子目录，用户同意再继续
- 可以并行派子 Agent：按扩展方向分，或多项目模式下每个项目一个。给子 Agent 的指令里要带上主题边界、词表、四类重点目标和切片清单格式，要求它只返回切片清单和证据，不要返回整段代码

## 第 5 步：内部切片清单（默认不交给学习者）

自己整理一份，作为写成品的底稿。每条五个字段：

```
文件:行区间 | 角色 | 相关度 | 为什么属于这个主题 | why 证据（提交/PR/issue 号，没有就写「无」）
```

**角色**（七选一）：

| 角色 | 含义 |
|---|---|
| 入口 | 外部从哪里进来 |
| 核心逻辑 | 主要实现 |
| 数据结构 | 状态怎么表示 |
| **配置与默认值** | 阈值、开关、默认策略 |
| **兜底与异常** | 失败了怎么办 |
| **测试** | 对预期行为的声明 |
| 文档与注释 | 作者自述的意图 |

**相关度**（三档）：`核心` / `相关` / `存疑`

采用覆盖优先，所以「存疑」的也要列进来，并写明为什么拿不准。

多项目模式：每个项目一份清单，**不要混在一起**。

**这份清单默认不进成品：**
- **学习者档：不输出。** 用户说「把涉及的文件列一下」才给，而且只给**文件名列表**，不给行号
- **开发者档：作为附录输出**
- **skill 规则产出：不输出**，证据在每条规则的「证据」字段里

## 多项目对比（多项目模式下，第 5 步之后、第 6 步之前做）

### 先各读各的

每个项目**独立**走完第 1–5 步，再开始对比。边读边比，最容易把 A 项目的做法安到 B 项目头上。

### 再做对比矩阵（内部底稿）

先从各项目的切片里归纳出**对比维度**——这个主题下需要做的几个决定。例（主题：上下文压缩）：
什么时候触发 / 压缩什么、保留什么 / 用什么方式压缩 / 压缩失败怎么办 / 用户能否干预。

```
维度 | 项目 A 做法 | 项目 B 做法 | 项目 C 做法 | 归类
```

**归类**（三选一）：

| 归类 | 判定 | 产出里怎么写 |
|---|---|---|
| **共识** | **定位相同的项目**之间做法实质相同；定位不同、这件事本来就交给了别的层的项目，记为「不适用」，不算反对 | 可以写成规则，标「多家一致（N/M，另有 K 家不适用）」 |
| **分歧** | 做法不同 | 找出**什么条件导致选择不同**（项目定位、规模、场景），写成「什么条件下选哪种」；找不到条件就写「分歧，原因未明」 |
| **独有** | 只有一个项目做了这件事 | 写成「参考做法」，并说明其他项目为什么没做（没需要 / 交给了别的层 / 原因未明） |

分歧的原因多半是推断，按防编造规则标出来。

**共识的两条警示：**
- **「多家一致」不等于「主流」。** 两三个项目是小样本，还可能互相借鉴。要称「主流做法」，必须再用 1–2 个同类项目或公开资料交叉验证，并在产出里写明验证了什么；否则只写「多家一致」。
- **共同「不做」要分辨。** 有作者理由的不做（例如「不自动删除，因为删错无法挽回」）可以写成规则；只是大家都没做、没有理由的（例如都不扫描敏感信息），是共同盲区，放进「本文没覆盖什么」，不写成规则。

## 深挖（多项目模式，对比矩阵之后、第 6 步之前做）

### 选深挖点

按顺序过滤：

1. **必要条件：对应目标 skill 的缺口。** 先读目标 skill 对应章节，列出它现在缺什么（缺参数、缺失败处理、缺判断条件……）。不对应缺口的机制，再有意思也不深挖。
2. **优先：多家一致的做法。** 按上面的「共识」定义（定位相同的项目一致，不适用的不算反对）。这类结论证据最硬，深挖后能直接写成「默认这样做」。
3. **共同「不做」**：只有带作者理由的才可以入选。
4. **最多保留 1 个分歧点**：只在它是目标 skill 使用者经常要面对的选择题时保留（例如「新旧冲突时原地改写还是追加」）。
5. **总数 2–4 个**。超过 4 个，深度会被摊薄，回到平均用力的老问题。

选完列给用户：每个点写「对应 skill 的哪个缺口 / 共识度 / 为什么选它」，用户确认后再深挖。

### 怎么深挖

- **按机制派子 Agent，不按项目派。** 同一个子 Agent 把机制 X 在所有项目里都读一遍，跨项目的差别和「设计写了、代码没接上」这类问题才看得出。指令里带上：主题边界、该机制在各项目的种子位置（来自广度段笔记）、机制卡格式、静默失败与踩坑的找法。
- **测试要读断言，不能只看用例标题。** 断言里的具体值就是边界条件。
- **默认值要查改动历史**：`git log -S`、`git log -L` 追到引入和修改它的提交，看提交说明和 PR 怎么说。
- **共识要下钻验证。** 大方向一致时，往下一层看参数和边界：常常是方向一致、取值差一个数量级（例如常驻上限一家 6.5 万字符、一家 1 万字符），这种差别照实写进机制卡。

### 机制卡（每个深挖点一张，内部底稿）

```
机制：
对应 skill 缺口：
共识度：多家一致（N/M，K 家不适用）/ 分歧
要解决的问题：
各家做法：每家一段，具体到代码路径和触发条件
关键参数：值 | 为什么是这个量级 | 调大会怎样 | 调小会怎样 | 依据（测试断言 / 提交 / 校准注释 / 问题单 / 推断）——量级理由和调大调小要分别标依据
边界条件：从测试断言读出的
静默失败点：哪里出错不报错、怎么发现
踩坑记录：相关 bug、修复、回滚——现象 → 原因 → 修法
不这样会怎样：具体后果
默认建议：默认这样做，除非……
```

**停止条件：** 每个字段要么填满，要么写「未找到」并说明找过哪里。不准留空。

## 第 6 步：产出

按第 0 步定的产出类型走 6A（文章）、6B（skill 规则），或两者都做。

### 6A：写文章

目标是让读者懂**作者为什么这么设计**，不是背下代码结构。

#### 学习者档的四条硬规则

##### 规则一：正文不出现行号，不贴代码块

出处只交代到**文件名**，而且在**每章（或全文）开头一次性列出**：

> 涉及源文件：agent-loop.ts、types.ts、tool-loop-detection.ts

之后正文里不再出现文件名和行号。

**行号对学习者没有价值**——他不会对着行号翻代码，只会被打断阅读。

唯一的例外：那段代码**本身极短（不超过八行）且是全文最关键的证据**，
比如一个只有七行、注释里写明了设计理由的配置文件。**全文最多一处。**
作者的注释、提示文案、PR 讨论用**引语**引，不用代码块。

##### 规则二：术语先解释再用，重要概念单独铺垫

动笔前先列一张表：这篇文章会用到哪些读者可能不懂的词？

- **普通标识符**：第一次出现时用一句话解释它是什么、单位是什么、默认值多少
  > 例：「`maxBytes` 表示允许处理的图片最大字节数，即体积上限，单位是字节，图片默认上限是 10MB。」
- **关键概念**：开一段（甚至一小节）专门铺垫，带日常例子
  > 例：讲「真实类型探测」之前，先用三段话区分「MIME 类型 / 声明类型 / 探测类型」，
  > 并举例「把图从微信存到本地，后缀是 .png 但内容实际是 JPEG 编码」

**宁可多花一段话解释，不要默认读者知道。**

##### 规则三：章节框架自己归纳，不能照搬代码结构

不要用「模块 A / 模块 B / 模块 C」或者「入口 / 核心 / 工具函数」做章节——
那是代码的组织方式，不是理解的组织方式。

**框架要从「这个设计在解决几类问题」里长出来。** 例如：

- 按层：输入层把图读对 → 选型层把模型选对 → 执行层把图片问对 → 输出层把结果规整对 → 容错层兜底
- 按策略：少做 / 早停 / 复用 / 并发

它们在源码目录里都不存在，是读完之后归纳出来的。

**一级标题必须是结论句。** 把所有一级标题抽出来连读，要能拿到完整论证。

##### 规则四：用「不这样会怎样」讲代价，不列优缺点

每个设计都要回答：

> 面对的问题是什么 → 他怎么做的 → **不这么做会怎样** → 代价是什么

「不这么做会怎样」要具体到后果，不是「会有问题」。例：

> 若直接采信声明类型，会有两种后果：一是把实际并非图片的文件当作图片送入模型，
> 只能得到空或错误的描述并浪费一次调用；二是即使确实是图片，若声明类型标错……

**没有代价的设计不是取舍，是常识。写不出代价就说明还没读懂。**

#### 学习者档的文章结构（单项目）

```
开头：一段说清楚这个设计要同时守住哪几个目标，以及全文怎么分
       （这里就要给出核心结论，不要吊着）

项目定位：一行
涉及源文件：一行列完，之后不再出现

正文：按自己归纳的框架分章，每章：
      这一层要解决什么问题 → 做了什么 → 为什么这么做（不这样会怎样）

刻意不做的事：这个项目明确不做什么、为什么（找到了就写，没找到写「未发现」）

应用示例：把这套设计落到一个具体场景上   ← 学习者最需要这一节

本文没覆盖什么：这个项目没处理、但使用者在同类场景里还要考虑的问题

结语：把各章收回主线

覆盖说明：读了什么、没读什么、快照（提交哈希 + 日期）、是否读了提交历史和 PR

核验清单：见下文「文末核验清单」
```

#### 学习者档的文章结构（多项目对比）

```
开头：这个主题要做哪几个决定；哪些是多家一致、哪些有分歧（直接给结论，必须过「结论自检」）

先判断：什么情况下根本不需要这套机制

贯穿原则：2–4 条，从全文反推；每条至少有两家的证据

项目定位表：每个项目一行（类型、场景、规模、快照日期）
涉及源文件：按项目各列一行

正文：按对比维度分章，每章：
      这个决定要解决什么问题 → 各项目怎么做 → 不这样会怎样
      └ 深挖机制：在所属章节里按机制卡完整展开——
        参数表（见「参数表的写法」）、边界条件、静默失败、踩坑、默认建议
      └ 非深挖维度：保持简要
      └ 章末小结表：共识 / 分歧 / 独有、共识度、证据强度

静默失败汇总：只作索引，每条一句话加章节号，不重复各章已展开的内容

应用示例：按读者的场景，说明每个维度该选哪种做法、参数取什么值、为什么

本文没覆盖什么：几个项目都没处理、但使用者还要考虑的问题（含共同盲区）

结语

覆盖说明：每个项目分别写；深挖段单独写读了什么

核验清单：见下文「文末核验清单」
```

**篇幅：** 深挖机制多、正文过长时，可以拆成上下篇：上篇写对比全景和贯穿原则，下篇写深挖机制。

**分类表：** 遇到「情况多、各自处理不同」时（例如哪类记忆该改写、哪类可追加），用表格让读者对号入座，不要写成一长段。

#### 参数表的写法

学习者档文章里的参数表默认用四列：

```
参数 | 值 | 有没有作者理由 | 主要风险
```

- 「有没有作者理由」：只写作者明说的取值理由（注释、提交、PR、文档、校准数据）。只说明了「为什么要有这个机制」、没说明「为什么是这个数」的，写「机制有说明；具体数值没有」。不同来源的话不能拼成一条理由。
- 「主要风险」：写调大或调小的后果。**每条后果都要标依据**：有测试断言、问题单或故障记录支撑的直接写；从代码可推出的写「（代码可推出）」；其余一律标「（推断）」。
- 没有信息量的格子（如「调大：文件更胖」「退出更慢」这类同义反复）写「—」，不要凑字。
- 阈值类参数先确认比较方向（`>=` 还是 `>`、分数越高越相似还是越不相似），再写调大调小的后果；方向写反是这类表格最常见的事实错误。
- 机制卡底稿可以保留完整的五列，但写进文章时按上面的规则压缩和标注。

#### 篇幅与去重压缩

文章初稿超过约 3 万字符时，交付前必须做一次去重压缩：

1. **同一机制、同一发现只在一处完整展开**。逐个检查高频发现（例如某个「设计写了、代码没接上」的问题、某个默认值）在全文出现了几次，只保留一处完整说明，其余改成一句话引用或删除。
2. **汇总表只当索引**：静默失败汇总、结语、核验清单不重复正文的论证。
3. **开头的结论和「贯穿原则」不重复**：两者内容重叠时合并，只留结论。
4. **故障经过压到两三句**：现象、根因、修法各一句。
5. **数字只在参数表写一次**，正文、默认建议、应用示例引用参数表或章节号。
6. **覆盖说明、涉及源文件、核验清单放附录**。

压缩后复查一遍：删掉的只能是重复和没有信息量的内容，不能删掉推断标注、未复核标注和反例。

#### 同一机制只在一处展开

一个机制往往同时服务多个目标（例如体积上限既保准确又保速度）。**只在一处完整展开**，其他地方用一句话引用（「体积上限见第二章」）并说明它在这里起什么作用。
按「目标」分篇（准确 / 速度）最容易把同一批机制讲两遍；优先按「处理阶段」或「决策维度」组织，在每个机制下顺带说明它对各目标的作用。

#### 限定词集中放，正文保持顺畅

共识度（「三家」「两家」）和证据强度集中放进**章末小结表**和核验清单；正文只在推断处标一次「（推断）」，不在每句话里反复加「两家」「见 x.x」。
理由：限定词散在句子里，核验方便了，学习却很累。

#### 术语检查

交付前扫一遍全文：每个专业词在第一次出现时都解释过吗？特别是工程常用词（游标、原子性、竞态、锁、幂等、半衰期……），对学习者都要一句话解释。

#### 本文没覆盖什么

**必写。** 列出这个（这些）项目没有处理、但读者在同类场景里还要考虑的问题，每条一句话说明为什么重要。例：「没有讲图片方向（EXIF）：手机照片不转正，模型看到的是歪图。」
这一节的内容来自你自己的判断，不是源码，**每条都标「补充」**，不能混进正文冒充项目做法。

#### 文末核验清单

**学习者档必写**（开发者档有切片清单时可省）。目的是让用户不读源码也能高效抽查。

挑 8–12 个**最关键、最容易错**的结论，每条一行：

```
序号 | 结论（一句话，对应正文第几节） | 出处文件 | 证据强度（作者明说 / 代码行为 / 推断） | 怎么查（看哪个函数、哪个常量、哪个 PR）
```

排序规则：**推断排最前**，其次是具体数字和默认值，最后是作者明说的。
正文里出现的所有默认值和数字，都要么进这张清单，要么在覆盖说明里说明为什么没进。
清单只放出处到文件和符号名，不放行号，不影响正文的阅读体验。

#### 交付前的结论自检（防说过头）

把所有一级标题和开头段的结论句抽出来，逐句回答：

1. 这句说的是「三家」「两家」还是「一家」，和正文的证据、章末小结表一致吗？
2. 有没有把「一家这么做」写成「应该这么做」，或把「多家一致」写成「主流」？
3. 「都」「只」「不」「从不」这类范围词，有没有比证据宽？

不一致就**改句子，不改证据**。

#### 应用示例这一节怎么写

**这是学习者档的必备节，不是可选。** 读者读完会问「那我能用到什么」。

做法：选一个读者可能碰到的具体场景，**把文中讲过的参数给出具体值和理由**。

> 例：「如果场景是用图片检测 5 项是否达标，这几个参数可以这样设：
>  maxBytes = 20MB：质检依赖细节，不要把正常高清图拒掉……
>  maxChars = 1500：要放下 5 条『满足/不满足加理由』，默认 500 会被截断……」

实在找不到合适场景，就写「这套设计可以借鉴到哪类系统上」，但**不准省略这一节**。

#### 开发者档的差异

只有三处不同，其余规则照旧：

1. 正文可以带 `文件:行号`，关键实现可以贴代码片段
2. 末尾附切片清单
3. 术语铺垫可以简化，但**项目特有的概念仍要解释**

文章写完要打磨时，转给写作迭代 skill；要重搓结构时，转给结构写作 skill。

### 6B：提炼成 skill 规则

目标是产出能直接并入某个 skill 的判断规则，不是文章。

#### 先读目标 skill

用户指定了要并入的 skill（如 ai-engineering-guide），先读它现有的内容。

**目标 skill 拆成「核心文件 + 参考文件」时**（如 SKILL.md 加 references/ 目录）：先读核心文件里的参考文件索引，再读和本主题对应的参考文件；没有对应文件时，判断是并入现有文件还是新建一个，在清单开头说明。每条规则要写明放入哪个文件；如果它属于「不读详版也必须做对」的判断，再标「建议同时进核心文件的必守要点」。

每条规则标出：

- **新增**：目标 skill 里没有
- **修订**：目标 skill 里有，但本次研究给出了更准的条件、代价或证据
- **冲突**：和目标 skill 现有说法相反——单独列出，交给人判断，不要自己选边

已经覆盖、本次没有新信息的，不列。

#### 规则格式

```
### <结论句：在什么情况下怎么做>
- 适用条件：什么场景、什么规模、什么前提下成立
- 做法：具体怎么做；有默认值的给量级和调整方向
- 为什么：不这样会怎样（具体后果）
- 代价与不适用：这么做付出什么；什么情况下别这么做
- 证据：项目 @ 快照日期 —— 强度（作者明说 / 代码行为 / 推断），附提交、PR、issue 号
- 共识度：多家一致（N/M，K 家不适用）/ 分歧（条件见上）/ 单项目；是否经额外交叉验证
- 关键参数：值、调大会怎样、调小会怎样（来自机制卡；非深挖规则可省）
- 改动类型：新增 / 修订 / 冲突
- 出自文章：确认版文章第几节（走确认闸门时必填）
- 放入：目标文件；是否建议进核心文件的必守要点
- 复查时间：建议半年后复查
```

#### 什么能写成规则

| 情况 | 写成 |
|---|---|
| 多家一致（定位相同的项目），且有中或强证据 | **规则**，标「多家一致」；经额外交叉验证后才可标「主流」 |
| 共同「不做」且有作者理由 | **规则**（写成「不要……，因为……」） |
| 共同「不做」但没有理由 | **不写成规则**，作为共同盲区放进文章的「本文没覆盖什么」 |
| 多项目分歧，找到了导致分歧的条件 | **条件选择**（「什么条件下选 A，什么条件下选 B」） |
| 单项目做法 / 只有一个项目做了 | **参考做法**，并写明项目定位 |
| why 只有推断、没有任何作者原话或代码证据 | **不写成规则**，放进「待验证」 |
| 运行时内核层面的设计，对用现成框架的团队不适用 | 写成**评估清单**（选框架时要问的问题），不写成照做的步骤 |

**不收录**：功能列表、安装步骤、稳定 API 的用法。
**例外**：变化快的框架 / SDK 的版本差异（新写法、已废弃写法）可以收录，必须标版本号。

#### 交付方式

只产出建议清单，**不直接改目标 skill**——由人核实后再合入。
清单开头写一段摘要：本次研究了什么、基于哪一版确认文章、几条规则 / 条件选择 / 参考做法 / 冲突 / 待验证、分别放入哪些文件。

## 防编造（硬规则）

### 最重要的一条：区分 what 和 why

**代码只能告诉你 what。why 是推断。**

| 强度 | 来源 | 怎么写 |
|---|---|---|
| 最强 | 注释 / commit message / PR 与 issue 讨论 / 文档里作者明说的 | 直接引，说明是作者原话及出处 |
| 中 | 代码行为本身（默认值、分支、测试断言） | 陈述事实 |
| 最弱 | 你自己的推断 | **必须标「推断」**，并说明依据 |

把推断写得像事实，是这类产出最常见的问题。

### 防编造靠的不是行号

**不带行号不等于可以乱写。** 真正的约束是这四条：

1. **只写实际读到的。** 第 5 步那份内部切片清单里没有的东西，正文不能出现（「本文没覆盖什么」一节除外，该节每条都标「补充」）。
2. **数字、默认值、文案必须核过。** 写进成品前回去重读一次那行。用子 Agent 研读时，正文里出现的**每个**数字和默认值，主 Agent 都要回到源码亲自核对；来不及核的，在核验清单里标「未复核」。
3. **不要把别的项目的做法当成这个项目的。** 模型对同类项目的先验很强，这里容易串。多项目模式下尤其要回到各自的切片清单核对。
4. **不要把单项目的做法写成通用规则。**

### 其余

- **没读到的就说没读到。** 文件太长只读了一部分、没读提交历史、没查 PR，都在覆盖说明里写出来。
- **泄露物要标来源。** 见第 0 步。
- **版本要标。** 每个项目都写快照（提交哈希 + 日期）。

## 全局硬规则

1. **默认写给学习者。** 判断不准就走学习者档。
2. **学习者档的正文不出行号、不贴代码块。** 出处只到文件名，且只在开头列一次。
3. **术语先解释再用。** 宁可多花一段。
4. **章节框架自己归纳，不照搬代码结构。** 一级标题必须是结论句。
5. **用「不这样会怎样」讲代价。** 没代价的不是取舍。
6. **文章产出的应用示例一节不准省。**
7. **覆盖优先，必须传递扩展，只能用第 4 步那三条停。**
8. **每条切片要写「为什么属于这个主题」。** 写不出来的别列。
9. **推断必须标出来。**
10. **一次只研究一个主题**（可以多个项目）。用户一次提两个主题就问先做哪个。
11. **克隆要保留提交历史**；只能浅克隆时在覆盖说明里写明。
12. **单项目只能产出「参考做法」，不能产出规则。**
13. **多项目先各自读完再对比，切片清单不混。**
14. **skill 规则只出建议清单，不直接改目标 skill。**
15. **目标是并入 skill 时，先出文章、停下等用户核验，再只从确认版文章提炼规则。** 文章里没有的结论不准出现在规则里。
16. **学习者档文章必带「本文没覆盖什么」和「文末核验清单」**；同一机制只在一处展开。
17. **多项目模式分广度、深挖两段**；深挖点 2–4 个，必须对应目标 skill 缺口，优先多家一致，最多 1 个分歧点，选完先给用户确认。
18. **「多家一致」按定位相同的项目算**，不适用不算反对；没经额外验证不称「主流」；没有理由的共同「不做」是盲区，不是规则。
19. **深挖机制必须讲到参数级**：量级理由、调大调小的后果、静默失败、踩坑；测试读断言，默认值查历史。
20. **交付前做结论自检**，正文每个数字都要主 Agent 复核或标「未复核」。
21. **参数表的调整方向（调大、调小的后果）必须标依据**：测试、问题单、故障记录支撑的直接写，代码可推出的标「代码可推出」，其余标「推断」；量级理由只写作者明说的，不拼接来源；阈值先确认比较方向。
22. **文章初稿超过约 3 万字符时，交付前做去重压缩**：同一发现只在一处展开，汇总表只当索引，数字只在参数表写一次，覆盖说明和核验清单放附录。
