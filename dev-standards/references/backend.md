# 后端规范

> 一句话：做接口、服务、数据库、异步任务时遵守的细则：怎么分层、数据库怎么改、错误怎么处理、怎么保证幂等、怎么鉴权、怎么让问题可排查。
> 来源：参考 affaan-m/everything-claude-code（backend-patterns）、supabase/agent-skills（postgres-best-practices）、wshobson/agents（backend-development、observability-monitoring）、goldbergyoni/nodebestpractices、trailofbits/skills（insecure-defaults）、OWASP Cheat Sheet Series，2026-10-10
> 相关：[开发规范主文件](../SKILL.md)、[接口契约与错误码](api-contract.md)
> 更新于：2026-10-10

示例以 Python 为主，Java、Go、Node.js 按同样原则执行。

## 一、技术栈约定

项目接入时由团队填写，AI 必须照这张表选型，不自己换：

| 类别 | 选型 |
|---|---|
| 语言与框架 | （团队填写，如 Python + FastAPI / Java + Spring Boot / Go + Gin） |
| 数据库 | （如 PostgreSQL / MySQL） |
| 数据库迁移工具 | （如 Alembic / Flyway / golang-migrate） |
| 缓存 | （如 Redis） |
| 消息队列 / 任务队列 | （如 Kafka / RabbitMQ / Celery） |
| 日志、指标、链路 | （如结构化日志 + Prometheus + OpenTelemetry） |
| 测试 | （如 pytest + testcontainers / JUnit + Testcontainers） |

## 二、分层架构

每个业务模块内部分三层，调用方向只能从上到下：

| 层 | 职责 | 禁止 |
|---|---|---|
| 接口层（Handler / Controller / api） | 解析参数、校验格式、调用 Service、组装响应 | 写业务逻辑、直接访问数据库 |
| 业务层（Service） | 业务规则、流程编排、事务边界 | 依赖 HTTP 请求对象等框架细节 |
| 数据访问层（Repository） | 数据库读写、对外部存储的访问 | 写业务判断 |

- **必须**：业务逻辑只放在 Service 层，接口层和数据访问层都要薄。
- **必须**：鉴权、请求日志、限流、链路标识注入这类所有接口都要的处理，放在中间件里统一做，不在每个接口里重复写。
- **必须**：Service 通过参数或依赖注入拿到 Repository，方便测试时替换。
- **禁止**：Repository 返回数据库连接、游标等底层对象给上层。

## 三、API 设计

接口的命名、响应格式、分页、版本、错误码统一按 [接口契约与错误码](api-contract.md) 执行。后端实现时额外注意：

- **必须**：响应只返回契约里定义的字段，**禁止**直接把数据库模型整个序列化返回（会泄露内部字段）。
- **必须**：列表接口必须分页，并设置每页上限（如 100 条），**禁止**无上限返回全量数据。
- **必须**：改接口保持向后兼容：只加字段、不删字段、不改字段含义和类型。必须做不兼容修改时，走新版本接口。

## 四、数据库

### 结构变更走迁移

- **必须**：所有表结构变更（建表、加字段、加索引）都写成迁移脚本，和代码一起提交，**禁止**手动在数据库上执行 DDL。
- **必须**：每个迁移脚本都能回滚（写好 downgrade）；删字段、删表、改类型这类不可逆操作，要单独评审。
- **必须**：大表变更分步做，保证新旧代码都能运行：
  1. 加新字段（允许为空）→ 2. 代码同时写新旧字段 → 3. 回填历史数据 → 4. 代码切换到只读新字段 → 5. 下个版本再删旧字段。
- **必须**：大表加索引用不锁表的方式（如 PostgreSQL 的 `CREATE INDEX CONCURRENTLY`）。
- **禁止**：修改已经在生产执行过的迁移脚本，要改就新增一个迁移。

### 查询与性能

- **必须**：查询条件、排序、关联用到的字段要有索引；新增慢查询相关的改动附上执行计划（`EXPLAIN`）。
- **禁止**：N+1 查询（循环里逐条查数据库）。改成批量查询或预加载关联数据。
- **禁止**：`SELECT *`，只查需要的字段。
- **必须**：使用连接池，设置合理的最大连接数和超时；**禁止**每个请求新建数据库连接。
- **必须**：大批量写入用批量操作，分批提交，每批有上限。

### 事务与并发

- **必须**：事务边界在 Service 层控制，一个业务操作一个事务，事务尽量短。
- **禁止**：在事务里调用外部 HTTP 接口、发消息、做耗时计算。
- **必须**：并发修改同一条数据时（扣库存、改余额），用乐观锁（版本号）或行锁（`SELECT ... FOR UPDATE`），**禁止**先查再改不加保护。
- **必须**：金额用定点数类型（`DECIMAL` / 整数分）存储和计算，**禁止**用浮点数。

## 五、错误处理

- **必须**：区分两类错误：
  - **业务错误**（参数不对、余额不足、订单状态不允许）：返回明确的错误码和提示，属于正常流程。
  - **系统错误**（数据库挂了、空指针、第三方超时）：记录完整日志和堆栈，对外只返回通用提示和 `trace_id`。
- **必须**：用统一的异常处理器把异常转换成 [规范的错误响应](api-contract.md)，不在每个接口里各写一套。
- **禁止**：把堆栈、SQL、内部路径、第三方原始报错返回给调用方。
- **禁止**：吞掉异常（`except: pass`、空的 catch）。确实要忽略，写注释说明原因，并记一条日志。
- **必须**：调用外部服务都设置超时，**禁止**无限等待。
- **必须**：只对可重试的错误重试（超时、网络抖动、5xx），用指数退避加随机抖动，设置最大次数；**禁止**对参数错误、4xx 重试。
- **建议**：频繁失败的下游加熔断，失败时有降级方案（返回缓存、默认值或明确的不可用提示）。

## 六、幂等与重试

幂等的意思是：同一个请求执行一次和执行多次，结果一样。网络重试、用户重复点击、消息重复投递都会导致重复请求。

- **必须**：创建订单、支付、扣款、发券这类写操作支持幂等。做法任选：
  - 客户端传幂等键（`Idempotency-Key` 请求头），服务端记录处理结果，重复请求直接返回第一次的结果；
  - 用业务唯一键加数据库唯一约束（如同一订单号只能有一条支付记录）；
  - 用状态机控制，只允许合法的状态流转（如只有「待支付」才能变成「已支付」）。
- **必须**：消息和异步任务的消费者必须幂等，因为消息队列一般只保证「至少投递一次」。
- **必须**：失败超过最大重试次数的消息进入死信队列，并触发告警，**禁止**无限重试或静默丢弃。
- **必须**：异步任务带上 `job_id` 和发起人信息，日志可追溯。

## 七、鉴权与授权

- **必须**：每个接口默认需要登录，不需要登录的接口要显式标记并评审。
- **必须**：除了校验「是否登录」，还要校验「有没有权限操作这条数据」。例如查订单时检查订单属于当前用户，防止改个 ID 就能看别人的数据（越权）。
- **必须**：权限校验放在后端，**禁止**依赖前端传来的角色、用户 ID 做判断；用户身份只从登录凭证里取。
- **必须**：密码用 bcrypt / argon2 加盐哈希存储，**禁止**明文或 MD5、SHA1。
- **必须**：登录、发短信、找回密码这类接口限流，防止暴力破解和刷接口。
- **禁止**：默认放行的配置。例如鉴权服务出错时应该拒绝请求，而不是放行；CORS **禁止**配置成允许所有来源并携带凭证。

## 八、缓存

- **建议**：默认用 cache-aside（旁路缓存）：读时先查缓存，没有再查数据库并写入缓存；写时先更新数据库，再删除缓存。
- **必须**：每个缓存都设置过期时间，并在代码注释里写明失效策略。
- **必须**：防三类问题：
  - **缓存穿透**（查不存在的数据，每次都打到数据库）：缓存空结果，设较短过期时间；
  - **缓存击穿**（热点数据过期瞬间大量请求涌入）：加互斥锁或提前刷新；
  - **缓存雪崩**（大量缓存同时过期）：过期时间加随机值。
- **禁止**：把缓存当成唯一的数据存储，缓存丢了必须能从数据库恢复。

## 九、可观测性

出了问题要能查到：谁、在什么时候、调用了什么、哪里出错。

- **必须**：用结构化日志（JSON），每条日志带 `trace_id`、`user_id`（或 `job_id`）、模块名。
- **必须**：日志分级使用：`ERROR` 需要人处理的问题，`WARN` 异常但可自动恢复，`INFO` 关键业务事件，`DEBUG` 排查细节（生产默认关闭）。
- **必须**：`trace_id` 在服务之间透传（HTTP 头、消息头），并在错误响应里返回给调用方。
- **必须**：核心接口记录请求量、错误率、耗时（P50 / P95 / P99）指标。
- **建议**：核心业务定义 SLO（服务质量目标，如「下单接口 99.9% 的请求在 500 毫秒内成功」），按 SLO 配告警。
- **禁止**：日志里出现密码、token、完整手机号和身份证号；需要时脱敏（如 `138****1234`）。

## 十、配置与密钥

- **必须**：配置按环境区分（开发、测试、生产），通过环境变量或配置中心注入。
- **禁止**：密钥写进代码仓库，包括测试配置文件和注释。
- **必须**：启动时校验必填配置，缺了直接启动失败并说明缺哪项，**禁止**带着默认值静默运行。

## 十一、测试

| 类型 | 测什么 | 写法 |
|---|---|---|
| 单元测试 | Service 层业务逻辑 | 用内存实现或测试替身替换 Repository |
| 集成测试 | Repository 和数据库、接口端到端 | 用真实数据库（testcontainers 拉起），**禁止**用 SQLite 代替生产数据库 |
| 契约测试 | 接口响应和契约是否一致 | 用契约文件自动校验响应结构 |

- **必须**：每个接口至少覆盖：正常情况、参数错误、未登录、无权限、数据不存在。
- **必须**：涉及并发和幂等的逻辑，写重复请求和并发请求的测试。
- **必须**：每个测试自己准备数据、自己清理，不依赖其他测试留下的数据。
