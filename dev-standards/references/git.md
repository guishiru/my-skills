# Git 规范

> 一句话：分支怎么开、提交信息怎么写、PR 怎么提、什么能提交什么不能，附 PR 模板和常见情况的处理办法。
> 来源：参考 Conventional Commits 1.0 规范、obra/superpowers（using-git-worktrees、finishing-a-development-branch）、GitHub Flow，2026-10-10
> 相关：[开发规范主文件](../SKILL.md)
> 更新于：2026-10-10

## 一、分支

- **必须**：主干分支（`main`）受保护：**禁止**直接推送，只能通过 PR 合并；合并前 CI 必须通过、至少一人评审。
- **必须**：从最新的主干拉分支，一个任务一个分支，做完合并后删除。
- **必须**：分支名格式 `类型/简述`，简述用小写英文加短横线，可带需求编号：

| 类型 | 用途 | 例子 |
|---|---|---|
| `feat` | 新功能 | `feat/order-refund` |
| `fix` | 修 bug | `fix/1234-login-timeout` |
| `refactor` | 重构，不改行为 | `refactor/payment-service` |
| `chore` | 构建、依赖、配置 | `chore/upgrade-node-20` |
| `docs` | 只改文档 | `docs/api-error-codes` |
| `hotfix` | 线上紧急修复 | `hotfix/pay-callback-500` |

- **建议**：分支存活不超过 3 天，太大的需求拆成多个可以独立合并的 PR，未完成的功能用功能开关隐藏。
- **建议**：需要同时处理多个任务时，用 `git worktree` 为每个任务开独立目录，避免来回切分支弄乱工作区。

## 二、提交信息

格式（Conventional Commits）：

```
类型(范围): 一句话说明

（可选）正文：为什么改、怎么改的、有什么影响

（可选）脚注：BREAKING CHANGE: ... / Closes #123
```

- 类型：`feat`、`fix`、`refactor`、`perf`、`test`、`docs`、`style`（只改格式）、`chore`、`ci`、`build`、`revert`。
- 范围：业务模块名，如 `order`、`user`。
- 说明：中文或英文团队统一一种，写「做了什么」，不超过 50 个字符左右，不加句号。

例子：

```
feat(order): 支持部分退款
fix(payment): 修复回调重复处理导致重复入账

支付渠道会重试回调，原逻辑没有按交易号去重。
改为按 channel_trade_no 加唯一约束，重复回调直接返回成功。

Closes #482
```

- **必须**：不兼容的改动在脚注写 `BREAKING CHANGE:` 并说明迁移方式。
- **禁止**：`update`、`fix bug`、`修改`、`wip` 这种看不出改了什么的提交信息合入主干。

## 三、提交粒度

- **必须**：一次提交只做一件事。重构和功能改动分开提交，格式化和逻辑改动分开提交。
- **必须**：每次提交都能编译通过、测试能跑过，方便以后用 `git bisect` 定位问题。
- **建议**：提交前用 `git diff --staged` 自查一遍，确认没有混入无关改动。
- **建议**：PR 合并时用 squash（压缩成一个提交）或保留整洁的提交历史，团队统一一种。

## 四、不能提交的内容

- **禁止**：密钥、token、密码、证书私钥、`.env` 文件。
- **禁止**：构建产物（`dist/`、`build/`、`target/`）、依赖目录（`node_modules/`、`.venv/`）。
- **禁止**：IDE 和系统文件（`.idea/`、`.DS_Store`、`Thumbs.db`）。
- **禁止**：大于 5MB 的二进制文件，需要时用 Git LFS 或对象存储。
- **必须**：依赖锁文件（`package-lock.json`、`pnpm-lock.yaml`、`poetry.lock`、`go.sum`）要提交。

**密钥不小心提交了怎么办**：立刻作废并更换这个密钥，这是第一步。只从历史里删掉是不够的，因为可能已经被拉取或缓存。然后再用 `git filter-repo` 清理历史，并通知团队。

## 五、危险操作

- **禁止**：在共享分支（`main`、`release/*`、别人也在用的分支）上 `push --force`。
- **建议**：自己的分支需要强推时，用 `git push --force-with-lease`，防止覆盖别人的提交。
- **禁止**：AI 未经确认执行 `git reset --hard`、`git clean -fd`、`git push --force`、删除分支这类会丢失代码的命令。
- **必须**：同步主干时团队统一用 `rebase` 还是 `merge`；推荐自己的分支用 `git pull --rebase` 保持历史整洁。

## 六、PR（合并请求）

- **必须**：PR 小而聚焦，建议改动不超过 400 行（不含自动生成的代码和锁文件）。
- **必须**：PR 标题和提交信息格式一致：`类型(范围): 说明`。
- **必须**：CI 全部通过才能请求评审，评审意见全部处理后再合并。
- **必须**：评审中「必须修改」的意见要改完，有不同意见在 PR 里讨论清楚，不要直接忽略。

### PR 描述模板

复制到项目的 `.github/pull_request_template.md`：

```markdown
## 做了什么
（一两句话说明这个 PR 解决什么问题，关联需求或 issue：Closes #）

## 为什么这样做
（关键的设计选择，考虑过但没采用的方案）

## 改动范围
- [ ] 只改了计划内的模块：（列出）
- [ ] 契约变更：无 / 有（文件 + 是否兼容）
- [ ] 数据库迁移：无 / 有（是否可回滚）
- [ ] 新增依赖：无 / 有（用途）
- [ ] 配置变更：无 / 有（各环境是否已配置）

## 怎么验证的
（check_done.sh 汇总输出，或测试命令和结果；界面改动附截图）

## 发现的其他问题（没有在本 PR 处理）
-

## 上线注意事项
（执行顺序、功能开关、回滚方式；没有就写「无」）
```

### 评审关注点

评审时按这个顺序看：

1. **对不对**：是否满足需求和契约，边界情况和异常有没有处理。
2. **安不安全**：鉴权、越权、输入校验、敏感信息。
3. **有没有越界**：是否改了无关模块，是否绕开了模块公开接口。
4. **测试够不够**：新逻辑有测试吗，测试测的是行为吗。
5. **好不好维护**：命名、结构、重复代码。
6. **性能**：N+1 查询、请求瀑布、大依赖。
