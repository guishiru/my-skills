# 前端规范

> 一句话：做页面、组件、样式、前端交互时遵守的细则：组件怎么拆、状态放哪、请求怎么写、性能和可访问性怎么验收。
> 来源：参考 vercel-labs/agent-skills（react-best-practices、composition-patterns、web-design-guidelines）、addyosmani/web-quality-skills（Core Web Vitals、可访问性）、anthropics/skills（frontend-design、webapp-testing）、OWASP XSS Cheat Sheet，2026-10-10
> 相关：[开发规范主文件](../SKILL.md)、[接口契约与错误码](api-contract.md)
> 更新于：2026-10-10

示例以 React + TypeScript 为主，Vue 等框架按同样原则执行。

## 一、技术栈约定

项目接入时由团队填写，AI 必须照这张表选型，不自己换：

| 类别 | 选型 | 说明 |
|---|---|---|
| 框架 | （团队填写，如 React 18 / Vue 3） | |
| 语言 | TypeScript（`strict: true`） | **禁止**新代码用 `any`，确实需要时用 `unknown` 再收窄 |
| 服务端数据 | （如 TanStack Query / SWR） | |
| 客户端状态 | （如 Zustand / Pinia） | |
| 样式 | （如 Tailwind / CSS Modules） | |
| 组件库 | （团队填写） | 已有组件能满足就不自己写 |
| 请求库 | 项目统一封装的请求层 | **禁止**在组件里直接调 `fetch` / `axios` |
| 测试 | Vitest / Jest + Testing Library + Playwright | |

## 二、组件架构

- **必须**：一个组件只做一件事。超过约 200 行，或者同时处理数据请求和复杂展示，就拆。
- **建议**：区分两类组件：负责取数和处理逻辑的容器组件，只根据 props 渲染的展示组件。展示组件不直接请求数据。
- **必须**：用组合代替一堆布尔 props。出现 `isCompact`、`showHeader`、`withFooter` 这类开关越来越多时，改成复合组件：

```tsx
// 不要这样
<Card showHeader isCompact withFooter footerText="..." />

// 改成这样
<Card>
  <Card.Header />
  <Card.Body compact />
  <Card.Footer>...</Card.Footer>
</Card>
```

- **必须**：props 传递超过两层，改用组合（把子组件作为 children 传进去）或 Context，避免层层透传。
- **必须**：可复用的逻辑抽成自定义 hook，命名 `useXxx`，放在所属业务模块内部。
- **禁止**：在渲染过程中产生副作用（请求、改全局变量、写 localStorage）。副作用放进事件处理函数或 effect。
- **建议**：列表的 `key` 用稳定的业务 ID，**禁止**用数组下标作为可增删列表的 key。

## 三、状态管理

先判断状态属于哪一类，再决定放哪：

| 状态类型 | 例子 | 放哪 |
|---|---|---|
| 服务端数据 | 订单列表、用户信息 | 服务端数据缓存库（TanStack Query 等），自带缓存和刷新 |
| 页面可分享的状态 | 筛选条件、分页、当前 tab | URL 参数 |
| 跨组件共享的界面状态 | 侧边栏开关、当前主题 | 客户端状态库或 Context |
| 只有一个组件用的状态 | 输入框内容、弹窗开关 | 组件内部 `useState` |
| 表单状态 | 表单字段、校验结果 | 表单库（如 React Hook Form） |

- **禁止**：把服务端数据复制一份存进全局状态库再手动同步。
- **必须**：同一份数据只有一个来源。能从已有状态算出来的值，直接算，不再单独存一份。
- **建议**：状态放在离使用它的组件最近的位置，不要什么都往全局放。

## 四、数据请求

- **必须**：所有请求走项目统一的请求层，由请求层统一处理鉴权头、错误码转换、超时、重试。
- **必须**：每个请求都处理三种状态：**加载中**、**出错**、**空数据**。三种状态都要有对应界面，不能只写成功的情况。

```tsx
if (isLoading) return <Skeleton />
if (error) return <ErrorState error={error} onRetry={refetch} />
if (!data?.length) return <EmptyState />
return <OrderList data={data} />
```

- **必须**：互相没有依赖的请求并行发出，不要一个等一个（请求瀑布）。
- **必须**：组件卸载或参数变化时取消过期请求，防止旧结果覆盖新结果。
- **必须**：请求和响应的类型从契约生成或与契约保持一致，**禁止**手写和契约不一致的类型。
- **必须**：错误提示按 [错误码规范](api-contract.md) 展示给用户能看懂的文案，不直接把后端错误信息或堆栈显示出来。
- **建议**：写操作成功后让相关查询失效重新拉取；体验要求高的场景用乐观更新，失败时回滚。

## 五、性能

### 验收指标（Core Web Vitals）

Core Web Vitals 是 Google 定义的三个页面体验指标，按真实用户第 75 百分位验收：

| 指标 | 含义 | 达标线 |
|---|---|---|
| LCP | 最大内容（主图、主标题）出现的时间 | < 2.5 秒 |
| INP | 用户点击、输入后页面响应的时间 | < 200 毫秒 |
| CLS | 页面加载过程中内容跳动的程度 | < 0.1 |

### 按影响从大到小的优化规则

1. **消除请求瀑布**（影响最大）：并行请求；能在服务端取的数据在服务端取；关键数据预加载。
2. **控制包体积**：路由级代码分割；大组件和不在首屏的内容懒加载；按需引入组件库和图标；**禁止**为一个小功能引入大依赖（如为格式化日期引入 moment）。
3. **图片和字体**：图片用现代格式（WebP / AVIF）并指定宽高，防止跳动；首屏外的图片懒加载；字体用 `font-display: swap`。
4. **减少不必要的重渲染**：状态下沉；拆分 Context；长列表用虚拟滚动。
5. **memo 要有依据**：`useMemo` / `useCallback` / `React.memo` 只在测量确认有性能问题时加，不默认全加。

- **必须**：首屏 JS 体积有明显增加（如超过 20KB gzip）时，在 PR 里说明原因。

## 六、UI 与设计

- **必须**：颜色、字号、间距、圆角、阴影都用 design token（设计变量），**禁止**在组件里写死颜色值和像素值。
- **必须**：适配移动端，在 375px 宽度下没有横向滚动条，可点击区域不小于 44×44px。
- **必须**：支持暗色模式的项目，新组件在两种主题下都要检查。
- **必须**：动效尊重系统的「减少动态效果」设置（`prefers-reduced-motion`）。
- **建议**：完成后在主要断点下截图自查，对照设计稿检查间距、对齐、文字截断。

## 七、可访问性

按 WCAG 2.2（网页无障碍国际标准）AA 级执行：

- **必须**：用语义化标签：按钮用 `<button>`，链接用 `<a>`，**禁止**用 `<div onClick>` 代替按钮。
- **必须**：所有功能能用键盘完成，焦点状态清晰可见，弹窗打开时焦点移入、关闭时焦点回到触发按钮。
- **必须**：图片有 `alt`（装饰图用空 `alt=""`）；图标按钮有 `aria-label`。
- **必须**：表单输入框都有关联的 `<label>`，错误信息和对应字段关联。
- **必须**：文字和背景对比度不低于 4.5:1（大字号不低于 3:1）。
- **禁止**：只靠颜色传达信息（如只用红色表示错误），要同时有文字或图标。

## 八、表单

- **必须**：前端校验规则和后端一致，最好共用同一份 schema（如 zod）；前端校验只为体验，后端必须再校验一次。
- **必须**：提交时禁用按钮或显示加载状态，防止重复提交。
- **必须**：错误提示显示在对应字段旁边，说清楚怎么改；提交失败时保留用户已填的内容。

## 九、安全

- **禁止**：用 `dangerouslySetInnerHTML` / `v-html` 渲染用户输入或接口返回的内容。确实需要渲染富文本时，先用 DOMPurify 之类的库清洗。
- **禁止**：把密钥、内部接口地址写进前端代码。前端代码对用户完全可见。
- **必须**：登录凭证优先放在 `HttpOnly` Cookie 里；放 localStorage 要评审并说明原因。
- **禁止**：只在前端做权限判断。前端隐藏按钮只是体验，真正的权限校验必须在后端。
- **必须**：跳转地址来自参数时校验白名单，防止被利用跳到钓鱼网站。
- **建议**：配置内容安全策略（CSP）响应头。

## 十、兼容与国际化

- **必须**：项目支持多语言时，界面文案全部走 i18n，**禁止**在组件里写死中文或英文。
- **必须**：日期、金额、数字按地区格式化（`Intl` API），金额计算用整数分或高精度库，**禁止**直接用浮点数算钱。
- **必须**：按团队约定的浏览器范围测试（团队填写，如 Chrome / Safari / 微信内置浏览器最近两个版本）。

## 十一、测试

| 类型 | 工具 | 写法 |
|---|---|---|
| 工具函数、hooks | Vitest / Jest | 输入输出断言 |
| 组件 | Testing Library | 按用户行为测：用 `getByRole`、`getByLabelText` 找元素，模拟点击和输入，断言用户能看到的结果 |
| 端到端 | Playwright | 只覆盖核心流程（登录、下单、支付），在接近真实的环境跑 |

- **必须**：优先用 `getByRole`、`getByLabelText` 找元素，找不到合适的再用 `data-testid`；**禁止**用 CSS 类名选元素，**禁止**断言组件内部 state。
- **必须**：组件测试覆盖加载中、出错、空数据三种状态。
- **建议**：关键页面加截图对比测试，防止样式被意外改坏。
