# 接口契约与错误码

> 一句话：前后端对接口的共同约定：契约怎么写、URL 怎么命名、响应和错误长什么样、分页和版本怎么做、什么样的改动算不兼容。
> 来源：参考 zalando/restful-api-guidelines、RFC 9457（HTTP 错误响应格式）、OpenAPI 3.1 规范，2026-10-10
> 相关：[开发规范主文件](../SKILL.md)、[前端规范](frontend.md)、[后端规范](backend.md)
> 更新于：2026-10-10

## 一、契约文件

- **必须**：每个接口在契约文件里定义，HTTP 接口用 OpenAPI 3（`openapi.yaml`），内部 RPC 用 protobuf。
- **必须**：契约里写清：路径、方法、请求参数（类型、是否必填、取值范围）、响应结构、可能返回的错误码、是否需要登录、是否幂等。
- **必须**：前端请求类型和后端校验模型从契约生成，或有测试保证和契约一致。
- **必须**：契约放在代码仓库里，改契约走 PR 评审，前后端都要有人看。

契约变更流程：

1. 先提交只改契约的 PR，前后端确认。
2. 后端实现，契约测试通过。
3. 前端对接。
4. 不兼容的改动按第六节走版本流程。

## 二、URL 命名

- **必须**：URL 表示资源，用名词复数、小写、短横线连接：`/api/v1/orders`、`/api/v1/refund-requests`。
- **禁止**：URL 里出现动词：不要 `/getOrder`、`/createOrder`。用 HTTP 方法表达动作。
- **必须**：子资源最多嵌套一层：`/orders/{orderId}/items`。
- 少数确实不是增删改查的动作，用 `资源/{id}:动作` 或 `资源/{id}/动作`，如 `POST /orders/{id}/cancel`，团队统一一种写法。

| 方法 | 用途 | 幂等 |
|---|---|---|
| GET | 查询 | 是 |
| POST | 创建、执行动作 | 否，需要时用幂等键 |
| PUT | 整体替换 | 是 |
| PATCH | 部分更新 | 视实现而定 |
| DELETE | 删除 | 是 |

- **禁止**：GET 请求修改数据。

## 三、字段约定

- **必须**：JSON 字段命名全项目统一一种风格（团队选定：`camelCase` 或 `snake_case`），**禁止**混用。
- **必须**：时间用 ISO 8601 格式并带时区：`2026-10-10T08:30:00+08:00`。
- **必须**：金额用整数分（`amountCent: 1999`）或字符串小数（`"19.99"`），**禁止**用浮点数。
- **必须**：ID 超过 JavaScript 安全整数范围（2⁵³）时用字符串传输，防止前端精度丢失。
- **必须**：枚举值用大写英文字符串（`"PAID"`），**禁止**用数字魔法值（`status: 3`）。
- **必须**：可选字段没有值时，团队统一是返回 `null` 还是不返回该字段，写进契约。

## 四、响应格式

成功时直接返回资源，HTTP 状态码表达结果：

```json
// GET /api/v1/orders/123  →  200
{ "id": "123", "status": "PAID", "amountCent": 1999 }
```

列表统一带分页信息：

```json
// GET /api/v1/orders?pageSize=20&cursor=xxx  →  200
{
  "items": [ ... ],
  "nextCursor": "yyy",
  "hasMore": true
}
```

- **建议**：数据量大或实时变化的列表用游标分页（`cursor`），后台管理类列表可以用页码分页（`page` + `pageSize` + `total`）。
- **必须**：`pageSize` 有默认值和上限（如默认 20，最大 100）。

> 如果团队已经统一用 `{ "code": 0, "data": ..., "message": "" }` 这种外包一层的格式，继续沿用，不要两种混用。新项目推荐上面的格式。

## 五、错误格式与错误码

所有错误统一返回下面的结构（参考 RFC 9457）：

```json
// 400
{
  "code": "ORDER_STATUS_INVALID",
  "message": "订单已发货，不能取消",
  "traceId": "a1b2c3d4e5",
  "details": [
    { "field": "orderId", "reason": "订单状态为已发货" }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `code` | 机器读的错误码，大写英文加下划线，前端按它判断怎么处理 |
| `message` | 给人看的说明，可以直接展示给用户，**禁止**包含堆栈、SQL、内部信息 |
| `traceId` | 链路标识，用户反馈问题时提供给开发排查 |
| `details` | 可选，参数校验错误时列出每个字段的问题 |

### 错误码命名

格式：`模块_错误描述`，如 `ORDER_NOT_FOUND`、`PAYMENT_BALANCE_INSUFFICIENT`、`USER_PHONE_DUPLICATED`。

通用错误码（所有模块共用）：

| HTTP 状态码 | 错误码 | 什么时候用 |
|---|---|---|
| 400 | `VALIDATION_FAILED` | 参数格式、类型、范围不对 |
| 401 | `UNAUTHENTICATED` | 没登录或登录过期 |
| 403 | `PERMISSION_DENIED` | 登录了但没有权限 |
| 404 | `RESOURCE_NOT_FOUND` | 资源不存在（或无权知道它存在） |
| 409 | `CONFLICT` | 状态冲突、重复创建、版本号冲突 |
| 422 | `模块_具体原因` | 参数格式对，但业务规则不允许 |
| 429 | `RATE_LIMITED` | 请求太频繁 |
| 500 | `INTERNAL_ERROR` | 系统内部错误，对外不暴露原因 |
| 503 | `SERVICE_UNAVAILABLE` | 依赖服务不可用、降级中 |

- **必须**：新增业务错误码登记在项目的错误码表里（如 `docs/error-codes.md` 或代码里的枚举），写明含义和前端怎么处理。
- **必须**：错误码一旦发布就不改含义、不复用。
- **必须**：前端按 `code` 判断逻辑，**禁止**按 `message` 文本判断。

## 六、版本与兼容

**兼容的改动**（可以直接发布）：

- 新增接口；
- 响应里新增字段；
- 请求里新增可选参数；
- 枚举新增值（前提：调用方对未知值有兜底处理）。

**不兼容的改动**（必须走版本流程）：

- 删除或重命名字段、接口；
- 修改字段类型或含义；
- 可选参数改为必填；
- 修改错误码含义、修改默认行为。

版本流程：

1. 新建版本路径（`/api/v2/...`），旧版本继续可用。
2. 在契约和响应头（如 `Deprecation`、`Sunset`）里标注旧版本的下线时间。
3. 确认所有调用方迁移后再下线旧版本。

- **必须**：客户端（前端、App）对响应里不认识的字段直接忽略，对不认识的枚举值有兜底展示。
