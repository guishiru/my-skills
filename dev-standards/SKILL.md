# 开发规范

> 一句话：让 AI 和人按同一套规矩写代码：先读契约，一次只做一件，不越界改动，测试和检查跑过、拿出证据才算完成。
> 来源：参考 obra/superpowers（计划、TDD、验证）、vercel-labs/agent-skills（React 性能与 UI 规则）、addyosmani/web-quality-skills（Core Web Vitals）、affaan-m/everything-claude-code（后端分层模式）、supabase/agent-skills（Postgres 规则）、trailofbits/skills（安全审查）、zalando/restful-api-guidelines（API 规范）、OWASP Cheat Sheet Series，按团队实践合并改写，2026-10-10
> 更新于：2026-10-10

## 怎么用这个 skill

主文件放所有任务都要守的规则。细则按任务类型再读，不用一次全读：

| 当前任务 | 还要读 |
|---|---|
| 页面、组件、样式、前端交互 | [前端规范](references/frontend.md) |
| 接口、服务、数据库、任务队列 | [后端规范](references/backend.md) |
| 新增或修改接口、错误码 | [接口契约与错误码](references/api-contract.md) |
| 提交代码、开分支、写 PR | [Git 规范](references/git.md) |
| 宣布完成之前 | 运行 `scripts/check_done.sh`，见第七节 |

**规则分三级**，AI 必须按级别执行：

- **禁止**：任何情况下都不能做。确实需要例外，先停下来问人。
- **必须**：每次都要做到。做不到要明确说出来，并说明原因。
- **建议**：默认这样做，有更好的理由可以不这样做，但要在汇报里说一句。

## 一、开发流程

每个任务按这 7 步走，不跳步：

1. **读需求和契约**：读 PRD、接口契约（OpenAPI、类型定义）、相关模块的公开接口。没读完不动手。
2. **澄清疑问**：需求有歧义、契约缺字段、验收标准不清楚，先问，不自己猜。一次把问题问全，最多 5 个。
3. **拆计划**：拆成每步 2–5 分钟能完成的小步，每步写清改哪个文件、怎么验证。超过 5 个文件的改动，先把计划给人确认。
4. **一次只做一件**：按计划逐步实现，一步做完验证过再做下一步。
5. **测试**：按第五节写测试、跑测试。
6. **自审**：对照本文件和相关细则检查一遍 diff，删掉调试代码、无用注释、多余改动。
7. **完成汇报**：跑完成检查，按第七节的模板汇报。

## 二、契约先行

- **必须**：先有契约再写实现。接口以契约文件为准（OpenAPI / protobuf / 共享类型定义），不以口头描述或现有代码为准。
- **必须**：实现和契约不一致时，以契约为准修实现；认为契约本身有问题，停下来提出，不要悄悄改成自己认为对的样子。
- **必须**：契约有改动，同一个 PR 里同步更新契约文件、前后端调用方和测试，并在 PR 描述里写明是否兼容。
- **禁止**：没有 PRD 或契约就开工写业务代码（纯技术重构、修 bug 除外）。

契约怎么写、错误码怎么定，见 [接口契约与错误码](references/api-contract.md)。

## 三、单任务开发与变更范围控制

- **必须**：一个任务、一个分支、一个 PR 只解决一件事。
- **禁止**：修改和当前任务无关的模块、文件、格式。包括顺手重命名、顺手调整格式、顺手升级依赖。
- **必须**：做的过程中发现别的问题，记到汇报的「发现的其他问题」里，不顺手改。
- **必须**：改动超出原计划的范围（多改了模块、要加新依赖、要改契约），先停下来说明原因，得到确认再继续。
- **禁止**：擅自引入新的第三方依赖。需要时说明用途、备选方案和体积或安全影响。

## 四、项目目录与模块边界

### 目录：按业务组织

- **必须**：按业务领域分目录（如 `order/`、`user/`、`payment/`），不按技术层（`controllers/`、`services/`）或前后端拆顶层。
- 每个业务模块内部再分层，结构示例：

```
src/
├── order/
│   ├── __init__.py      # 公开接口：别的模块只能用这里导出的东西
│   ├── api.py           # 接口层（路由、参数解析）
│   ├── service.py       # 业务逻辑
│   ├── repository.py    # 数据访问
│   └── tests/
├── user/
└── shared/              # 真正通用、无业务含义的代码（工具函数、基础类型）
```

前端同理：`src/order/index.ts` 是公开入口，组件、hooks、请求放在模块内部。

- **禁止**：往 `shared/` 里放带业务含义的代码。只有一个模块用的代码，放回那个模块。

### 模块边界：只走公开接口

- **必须**：跨模块只能用对方公开入口（`__init__.py` / `index.ts`）导出的函数和类型。
- **禁止**：跨模块直接引用对方的内部文件（如 `from order.repository import ...`）。
- **禁止**：跨模块直接读写对方的数据库表。要数据就调对方的公开接口。
- **必须**：跨模块调用要能追溯是谁发起的：带上 `user_id`、`session_id` 或 `job_id`。做法任选其一：作为第一个参数传 `ctx`（上下文对象），或者用 `contextvars` / 请求上下文自动透传；日志里必须能看到这些标识。
- **禁止**：模块之间循环依赖。

### 依赖方向：由测试强制

模块之间谁能依赖谁，写在 `test_module_boundaries.py` 的 `ALLOWED` 表里：

```python
ALLOWED = {
    "order":   {"user", "payment", "shared"},
    "payment": {"shared"},
    "user":    {"shared"},
    "shared":  set(),
}
```

- **必须**：新增模块时同时在 `ALLOWED` 表里登记，否则测试不通过。
- **必须**：新增依赖方向要改 `ALLOWED` 表，改表的 PR 要有人评审。
- **禁止**：为了让测试通过，绕开公开入口或者把代码挪进 `shared/`。

## 五、测试规则

- **必须**：新功能带测试，测试和实现在同一个 PR 里。
- **必须**：修 bug 先写一个能复现问题的失败测试，再修，修完测试变绿。
- **建议**：业务逻辑优先用 TDD：先写失败的测试，再写刚好让它通过的代码，再重构。
- **必须**：测试按用户能观察到的行为写（输入什么、得到什么），不测内部实现细节。
- **必须**：只 mock 外部依赖（第三方服务、网络、时间、随机数），不 mock 自己项目里的其他模块。
- **禁止**：删除、注释掉或 skip 已有测试来让 CI 通过。测试确实过时了，在 PR 里单独说明为什么删。
- **禁止**：为了让测试通过而改测试的预期值，除非需求本身变了，并在 PR 里写明。
- **必须**：测试之间互不依赖，可以单独跑、乱序跑。

测试分层：

| 层级 | 测什么 | 比例 |
|---|---|---|
| 单元测试 | 业务逻辑、工具函数、组件行为 | 最多 |
| 集成测试 | 接口 + 数据库、模块之间的协作 | 中等 |
| 端到端测试 | 核心用户流程（下单、支付、登录） | 少，只覆盖关键路径 |

前后端各自的测试工具和写法见对应细则。

## 六、Git 规范（要点）

- **必须**：从最新主干拉分支，分支名 `类型/简述`，如 `feat/order-refund`、`fix/login-timeout`。
- **必须**：提交信息用 Conventional Commits 格式：`类型(范围): 说明`，如 `fix(order): 修复退款金额精度丢失`。
- **必须**：小步提交，每次提交都能编译、测试能过。
- **禁止**：提交密钥、`.env`、构建产物、`node_modules`、大文件。
- **禁止**：在共享分支上 `push --force`；禁止直接往主干推送。
- **必须**：PR 描述写清做了什么、为什么、怎么验证的，用 [Git 规范](references/git.md) 里的模板。

## 七、完成标准（DoD）

下面每一项都满足，才能说「完成」：

| 检查项 | 怎么证明 |
|---|---|
| 所有测试通过 | 测试命令的输出 |
| lint 和格式检查通过 | lint 命令的输出 |
| 类型检查通过（有类型系统的项目） | 类型检查命令的输出 |
| 模块边界测试通过 | `test_module_boundaries.py` 的输出 |
| 实现和契约一致，契约改了已同步 | 列出改动的契约文件，没改就写「无」 |
| 没有越界改动 | `git diff --stat` 里只有计划内的文件 |
| 没有遗留调试代码和密钥 | 完成检查脚本的扫描结果 |

- **必须**：宣布完成前运行 `scripts/check_done.sh`（或项目里等价的命令），把结果附在汇报里。
- **禁止**：没跑检查就说「完成了」「应该可以了」「理论上没问题」。没跑就说没跑，并说明原因。
- **禁止**：检查失败时报告成功。部分失败要如实列出。

**完成汇报模板**：

```
## 完成情况
做了什么：（一两句话）
改动文件：（列表，说明每个文件为什么改）
契约变更：无 / 有（文件 + 是否兼容）

## 验证证据
（check_done.sh 的汇总输出，或测试、lint、类型检查的命令和结果）

## 发现的其他问题（没有顺手改）
- ...

## 需要人确认的事
- ...
```

## 八、调试方法

1. **先复现**：找到稳定复现的步骤，最好写成失败测试。
2. **再定位**：看日志、加断点、二分排查，确定问题出在哪一层。
3. **找根因**：问「为什么」直到找到真正原因，不只修表面症状。
4. **再修复**：修根因，跑复现测试和全量测试。

- **禁止**：不知道原因就改代码试试看；连续试了 3 次还没解决，停下来整理已知信息再继续，或者向人求助。
- **禁止**：用吞掉异常、加 `try/except: pass`、加大超时这类办法掩盖问题。

## 九、安全底线

- **禁止**：在代码、配置文件、日志、测试数据里写密钥、密码、token。用环境变量或配置中心。
- **必须**：所有外部输入（请求参数、文件、第三方回调）都要校验类型、长度、范围。
- **必须**：数据库查询用参数化，禁止拼接 SQL。
- **必须**：每个接口都鉴权，并校验当前用户有没有权限操作这条数据。
- **禁止**：日志里打印手机号、身份证、银行卡等敏感信息的明文。
- **必须**：权限最小化：服务账号、数据库账号、token 只给需要的权限。

前后端各自的安全细则见对应文件。

## 十、自动化强制

规则只写在文档里会被忘，下面这些让规则在提交和 CI 时自动检查：

| 工具 | 检查什么 | 放在哪 |
|---|---|---|
| `scripts/test_module_boundaries.py` | 模块是否登记、是否只走公开入口、依赖方向是否在 `ALLOWED` 表内、有没有循环依赖 | 复制到项目的 `tests/` 下，pytest 会自动收集；也能直接 `python test_module_boundaries.py` 运行 |
| `scripts/check_done.sh` | 测试、lint、类型检查、边界测试、密钥扫描、改动范围，一次跑完并输出汇总 | 复制到项目的 `scripts/` 下，完成前和 CI 里运行 |
| `assets/pre-commit-config.yaml` | 提交前跑格式化、lint、密钥扫描、提交信息格式 | 复制为项目根目录的 `.pre-commit-config.yaml`，执行 `pre-commit install` |
| `assets/github-ci.yml` | PR 上自动跑 `check_done.sh` | 复制为 `.github/workflows/check.yml` |

**接入新项目的步骤**：

1. 复制上面四个文件到项目对应位置。
2. 打开 `test_module_boundaries.py`，按项目实际改 `MODULE_ROOTS`（模块放在哪个目录）和 `ALLOWED` 表。
3. 本地运行 `bash scripts/check_done.sh`，确认能跑通。
4. 在代码托管平台把 CI 检查设为合并 PR 的必要条件。

AI 在项目里发现这些文件不存在时，**建议**提醒人接入，但不要未经同意自己加进去（属于越界改动）。

## 禁止清单速查

1. 没读契约就写业务代码。
2. 改和当前任务无关的文件。
3. 擅自加新依赖。
4. 跨模块引用内部文件或读写对方的表。
5. 删测试、skip 测试、改预期值来让 CI 通过。
6. 提交密钥和敏感信息。
7. 往共享分支 force push，直接推主干。
8. 没跑检查就说完成，检查失败报成功。
9. 不知道原因就乱改代码试。
10. 吞掉异常掩盖问题。
