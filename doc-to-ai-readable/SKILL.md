# 文档转 AI 可读格式

## 为什么要转

金字塔原理是为人设计的：默认读者有背景、会整篇连读，作者要说服读者。AI 读文档的条件不一样：

| 写给人的习惯 | AI 遇到的问题 | 改写方向 |
|---|---|---|
| 默认读者懂背景 | AI 没有背景 | 写明范围、前提、口径 |
| 为说服而组织 | AI 要能核对 | 结论和依据写在一起 |
| 整篇连读 | 只拿到片段或只读一遍 | 去掉指代和相对时间 |
| 精炼、留暗示 | 暗示被当成事实，或被忽略 | 明说假设、不确定性、例外 |
| 数字写在句子里 | 难抽取，易算错 | 改成表格，带单位、口径、时间、来源 |

“结论先行”保留。

## 两种格式，二选一

| | A. Agent 上下文 | B. 知识库 / RAG |
|---|---|---|
| 下游怎么用 | Agent 整篇加载，照着执行或判断 | 切块入库，提问时只检索出一两块 |
| 组织方式 | 按“怎么做”：规则、步骤、分支、禁令 | 按“能回答什么”：每块是一个独立事实单元 |
| 关键要求 | 可执行、无歧义、拿不准时有兜底 | 每块单独读得懂、容易被检索命中 |

**每次开始转换前，都必须用 AskUserQuestion 和用户确认用哪一种。** 选项就是 A 和 B。

- 不设默认，也不要根据文档类型自行决定。可以在选项说明里写一句“这类文档通常选 X”供参考。
- 选定后，本次所有文档只用这一种格式输出，不混用。
- 用户中途要改格式，就按新格式重新输出全部文档。

## 铁律

失败有两个方向：

- **补充过度**：编造事实、加强语气。
- **标注过度**：把写清楚的事标成待确认，堆满编者注。

两种都会误导下游。标注过度还会让 Agent 无谓升级、多问用户。

1. **不新增事实。** 只重组、显化原文已有的信息。推断出的内容标 `[推断：依据]`。
2. **原文没有的字段值写“未提供”。** 不要自己填状态、负责人、日期。
3. **不改语气强度。** 不增删“一律、主要、建议、可以考虑、初步”这类词。
4. **不把要求推成禁令。** 禁止事项只收原文明确写了“不得、禁止、不在范围”的内容。
5. **只给真歧义标 `[待确认]`。**
   - 标之前先通读全文，看别处有没有已经说清。例如“以上情况都要在质保期内”已经覆盖了后面的特例。
   - 两种读法会得出不同的结论或动作时才标。不影响结论的含糊不标。
6. **拆列表时保留共享修饰语。** 例如原文“A、B、C 导致的损坏”，拆开后每项都要写成“……导致的损坏”。
7. **跨文档信息单独标注。**
   - 写成 `编者注（据 <doc_id>）：…`，不混进正文。
   - 别名、负责人、frontmatter 字段里用到的跨文档信息也一样。
8. **原文矛盾时保留两种说法**，标 `[冲突]`。
9. **缺失的派生数字写“未测算”。** 不替下游代算。
10. **字面意思不算推断。** “低于、不足、大于、及以上、更换后”这类原文字面已经说明的，直接写，不标 `[推断]`。
11. **升级和兜底动作沿用原文语气。**
    - 原文写“可联系区域售后经理”，就写“可联系”，不写成“必须升级给”。
    - 原文没写的兜底动作标 `[推断]`。

## 流程

### 第 1 步：读入

- **粘贴文本、Markdown**：直接读。
- **Word**：
  - 先执行 `pip install 'markitdown[docx]' --break-system-packages`，再执行 `markitdown f.docx`。
  - 失败时用 `pandoc -t gfm f.docx`。
  - 转完检查四处：
    - Word 的“标题”样式是否变成了普通段落
    - 表格是否完整
    - 表头是否错位成了第一行数据（markitdown 常见）
    - 编号列表是否完整
- **多篇**：先列清单（文件、标题、日期、类型、可能的版本关系），请用户确认范围。

### 第 2 步：确认格式（必做）

用 AskUserQuestion 问一个问题：“整理后的文档给 AI 怎么用？”

- **A. 给 Agent 当上下文**：Agent 照着执行或判断。SOP、制度、操作规范通常选这个。
- **B. 进知识库（RAG）**：切块检索问答。纪要、周报、汇报、FAQ 通常选这个。

多篇文档时，在问题里列出文档清单，一次确认一种格式。这一步可以和第 1 步的范围确认放在同一轮提问里。

### 第 3 步：识别类型与关系

- 文档类型：汇报/周报、方案、复盘、纪要、SOP/制度、调研。
- 多篇时，还要识别：
  - 版本替代关系
  - “后文档的决议覆盖前文档的建议”这类关系

### 第 4 步：缺失检查

**必要信息**（缺了会导致误用）：

- 成文日期
- 数据统计区间
- 适用范围
- 核心指标口径
- 结论或规则的主体
- 版本与有效性

选 A 格式时，还要查：

- 数值区间的边界
- 金额、里程这类数值具体指什么
- 从何时起算
- 例外情形

**处理顺序：**

1. 多篇时，先用同批其他文档补全，并按铁律 7 标出处。
2. 仍缺的，汇总成**一轮**提问：最多 5 题，每题附原文出处，影响判断路径的问题优先问。
3. 用户也答不上来的，标 `[待确认]` 继续。

只问会改变结论或动作的问题。货币单位、显而易见的年份这类不问。

**非必要信息**缺了，只写“未提供”，不追问。

### 第 5 步：抽取与改写

**抽取内容：**

- 结论
- 依据数据
- 假设
- 术语
- 规则或决议
- 行动项
- 风险
- 纪要类还要保留共识和表态

**改写规则：**

- **去指代**：“该方案”“它”“那边”换成具体名称。
- **绝对时间**：
  - 用脚本推算星期和日期，例如 `python3 -c "import datetime as d;print(d.date(2026,10,10).strftime('%A'))"`。
  - 标注里写明推算基准，例如 `2026-10-16 [推断：原文“下周五”，会议日 2026-10-10 周六]`。
  - 只缺年份时，在 frontmatter 的 date 上标一次 `[推断]`，正文不再逐处重复。文档自己写了年份的，不标。
- **数字写全**：单位、口径、时间、来源都要有。
- **术语统一**：
  - 同一概念只用一个名字，别名放进术语表。
  - 易混的概念要写明区别，例如“短信召回 ≠ 企微触达”。
- **编号带简称**：写成“R2c（扎钉无法修补）”，不要只写“R2c”。
- **去掉修辞**：删客套、铺垫和重复。

### 第 6 步：按选定格式输出

#### 共用 frontmatter

```yaml
---
doc_id: <类型>-<YYYYMMDD>-<短名>   # rpt/sop/mtg/plan/rev/res/wkly
title:
format: agent | rag
doc_type: 汇报|周报|方案|复盘|纪要|SOP|制度|调研
status: 草稿|定稿|已过期|已替代|未提供
date: YYYY-MM-DD
data_period:
scope:
owner:
valid_until:
supersedes: / superseded_by:
related: []
source:
tags: []
---
```

#### A. Agent 上下文格式

整篇会被一次性加载，所以重点是可执行，不需要每块自带出处。

```markdown
# <标题> <版本>
> TL;DR：<一句话：本文让 Agent 做什么、何时生效、替代了什么>

## 何时使用本文
- 适用：…
- 不适用：…
- 部分适用：…（写明哪部分适用、哪部分转查何处）

## 术语与口径
| 术语 | 定义 | 别名 |

## 核心规则
### R1 <简称>
规则正文（祈使句，一条一事）。例外：…。配套表格和 [待确认] 也放在这里。

## 操作步骤
1. <步骤>（前置条件：…；时限：…；产出：…）

## 判断分支
- 如果 <条件>，则 <动作>（依据：R#（简称））
- 推断出的分支标 [推断]

## 禁止事项
- 只列原文明说的

## 拿不准时
- 原文指定了联系人的，按原文语气写。原文是“可联系区域售后经理”，就写“可联系区域售后经理”。
- 原文没有指定的，写“停下并询问用户 [推断]”。
- 每个 [待确认] 都要写明 Agent 此时该怎么做。

## 背景与依据（可选，压缩成简表）
```

**篇幅：**

- Agent 每次都要整篇加载，A 格式成品一般控制在原文的 3 倍以内。
- 原文本来就是条理清楚的 SOP 时，只做必要的显化，不要逐条加注。
- 同一个 `[待确认]` 只在规则处写一次，“拿不准时”里只引用，不再展开。

**汇报、纪要这类文档选了 A 格式时**，结构不变，内容这样对应：

- 决议 → 核心规则
- 待办 → 操作步骤，写明负责人和截止日
- 结论和数据 → 背景与依据

#### B. 知识库 / RAG 格式

文档会被切块检索，所以重点是每块单独读得懂、容易被命中。

```markdown
# <标题>
> TL;DR：<一句话结论，含主体、时间、范围>

## <章节：如 结论 / 决议 / 数据 / 规则 / 待办 / 术语 / 风险>

### <块标题：本身就是一句完整的话>
> 出处：<标题> <版本>｜<日期>｜<适用范围>

<首句自带时间和场合，例如“2026-10-10 复购复盘会决议：…”。>
<关键数字、口径、依据直接写在块内，不引用块外的编号。>
<相关的表格、例外、[待确认] 放在同一块。>

可回答：<1–3 个用户可能问的问题>
```

- 标题层级：`#` 是文档，`##` 是章节，`###` 是检索块。
- 每块控制在 200–600 字。
- 术语表单独成一块。块内用到易混术语时，括注一句定义。
- 不写“如上所述”“见上文”。
- 去重：同一个编者注或风险提示，只放在真正需要它的块里，一句话写完。不要在 INDEX、每篇正文、每个块里各写一遍。

#### 已替代文档（两种格式通用）

- 输出一个存根，`status: 已替代`。
- 顶部写警示：“勿引用本文数字，以 <新 doc_id> 为准”。
- 列出版本差异表：数字变化、语气变化、新版删掉的内容。
- 只在旧版出现的信息，原样保留，不加评价。

### 第 7 步：多篇文档

- 每篇输出一个 `<doc_id>.md`，全部使用选定的同一种格式。
- 另外生成 `INDEX.md`（llms.txt 风格），依次包括：
  - H1：知识集名称
  - 引用块：本知识集的格式、覆盖范围、资料截止日期、优先级规则
  - `## 文档`：链接：一句话说明｜日期｜status
  - `## 关系`：替代、覆盖、冲突
  - `## Optional`：已替代或次要的文档
- 旧文档里已被后续文档覆盖的内容，加 `编者注（据 <doc_id>）`。
- 跨篇检查三项：
  - 同一指标的数字是否一致
  - 同一事项的负责人是否一致
  - 术语是否统一

### 第 8 步：自检

**两种格式都要查：**

- [ ] 逐句对照原文：没有新增事实，没有编造字段值，每个 `[推断]` 都写了依据
- [ ] 禁止事项都能在原文里找到对应的话
- [ ] 拆开的列表项都保留了共享修饰语
- [ ] 会改变结论的歧义都标了 `[待确认]`
- [ ] 跨文档信息都写成了编者注，并带 doc_id
- [ ] 语气词没有增删
- [ ] 数字和日期逐一核对过，星期用脚本验证过
- [ ] 纪要类的共识和表态没有丢
- [ ] 逐个复核 `[待确认]`：原文别处是否已经说清？两种读法的结论是否真的不同？不是就删掉
- [ ] 逐个复核 `[推断]`：是不是只是字面意思？是就去掉标签
- [ ] 升级和兜底动作的语气和原文一致

**只针对 A 格式：**

- [ ] 每条规则都有明确的触发条件
- [ ] 每个 `[待确认]` 都写了 Agent 的兜底动作
- [ ] 步骤写明了前置条件和时限
- [ ] 成品长度在原文 3 倍以内，或能说明为什么需要更长

**只针对 B 格式：**

- [ ] 随机抽 3 块单独读，都看得出主体、时间、范围
- [ ] 块内没有引用块外的编号
- [ ] 每块都有出处行和“可回答”

### 第 9 步：交付

- 单篇输出一个 `.md` 文件；多篇输出一个目录，含 INDEX.md。
- 回复用三五行说明：
  - 用了哪种格式、处理了几篇
  - 还剩哪些 `[待确认]` 和 `[冲突]`
