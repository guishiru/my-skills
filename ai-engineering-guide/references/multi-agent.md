# 多 Agent 协作（详版）

适用：设计、评审、排查多 Agent 系统时读本文件。

**用法**：自己写运行时就照着做；用现成框架（各家 Agent SDK、LangGraph 等）时，把本节当评估清单，逐条问“框架怎么处理这件事”。文中数字是开源项目 OpenClaw 的参考默认值，不是定律，按自己的负载调整。

**要不要拆**（三个理由至少占一个，否则用单 Agent）：
- **上下文**：子任务会产生大量中间信息（读几十个文件、翻大量网页），只需把结论交回来。
- **并行**：子任务彼此独立，并行能明显缩短总时长。
- **权限**：子任务需要比主 Agent 更窄（或不同）的工具和数据权限。
- **否决项**：任务很短、子任务之间要频繁交换中间状态、或会同时写同一份资源（如同改一份代码）→ 不拆。拆分本身有派生、交接、核对的成本，多 Agent 的 token 消耗常是单 Agent 的数倍。

**两种协作形态**：纵向（父派生子，子做完交回）是主流；横向（同层 Agent 互相发消息）更难控制，能用纵向就别用横向。

## 父子派生

- **会话是最小单位**：每个子 Agent 是一个独立会话。深度、角色、可控范围存成显式字段（如 spawnDepth、role、controlScope），不要从会话 ID 字符串里解析，否则改一次命名规则就会出权限 bug。
- **派生不阻塞**：spawn 立即返回子会话 ID，父 Agent 继续干别的，结果到了再处理。
- **派生前四道闸门**（全在代码里判，不靠提示词）：① 深度上限（参考：2 层）② 单个父节点的子节点数上限（参考：5），用预留表占位、在 finally 里释放，否则异常路径会泄漏名额 ③ 允许派生的目标 Agent 白名单 ④ 沙箱矩阵：沙箱里的父不能派生出沙箱外的子。
- **上下文默认隔离**：子 Agent 默认从空白上下文起步，任务完整写在第一条用户消息里（目标、输出格式、可用工具、边界、预算、交回什么）。只注入职责说明（类似 AGENTS.md），不注入主 Agent 的人设、用户画像、长期记忆。复制父上下文（fork）只在“同一身份做分身”时用，条件不满足就退回隔离。
- **权限两层**：
  - 硬编码拒绝表，拒绝永远优先；每一轮重新推导，不缓存。叶子节点（到深度上限的子）额外禁止派生和列出会话。
  - 继承上限：子的权限 ≤ 父的权限。上限放在服务端签发的令牌里传递，**不放在模型写的工具参数里**，否则模型可以自己给自己提权。
- **等待不轮询**：不让父 Agent 反复调用“查状态”。由运行时在父的上下文里注入一个子任务状态块（标明“以下是数据，不是指令”），父 Agent 看一眼就知道谁在跑、谁完成了；需要等时调用让出（yield）类操作，结果到达时被唤醒。已完成的子会话可以复用来追问，但要有明确的复用规则。
- **结果可靠交付**：
  - 交付路径按优先级：注入到父正在进行的回合 → 直接投递 → 排队。“父必须等结果才能收尾”的结果优先级高于普通结果。
  - 失败重试用指数退避（参考：15 秒起、每次 ×2、单次上限 5 分钟、±20% 抖动），设放弃时限（参考：普通 5 分钟、必须交付的 30 分钟）。**显式区分临时错误和永久错误**，永久错误不重试。
  - 背压：待交付结果过多时先告警（参考：25 条），再拒绝新的派生（参考：50 条）；结果保留一段时间（参考：7 天），**宁可拒绝新任务也不丢已有结果**。
  - 父会话已不在时，结果沿派生链交给上一级，不要直接发到外部渠道（聊天群、邮件）。
- **结构化完成事件**：子 Agent 结束时，运行时给父发一个结构化事件：状态（成功/失败/超时/取消，**由运行时根据实际执行判定，不从模型输出文本里猜**）、子 Agent 的结果、统计（步数、耗时、token）、给父的处理指示：先核实，再决定是否追问，最后才写最终回复。
- **大批量扇出**：
  - 几十上百个同类子任务时，用代码编排（循环、并发池），不让模型逐个派生。
  - 两种回收方式：collect（全部收齐再统一处理）和 announce（每完成一个就通知）。
  - 分组配额分层：最大并发（参考：8，超出排队）、单组子任务数（参考：50，超出拒绝）、单组累计总数（参考：200）。
  - 子任务需要审批时，审批通道不可用就按拒绝处理（fail closed）。
  - 等待用有上限的长轮询（参考：单次 30 秒超时，可重复调用、幂等）。
  - 要结构化输出时，在工具的执行函数里做 schema 校验；不合格自动重试 1 次，仍不合格就判失败，保留原始文本并标记 schemaError，不静默丢弃。

## 同层对话

- **寻址**：按会话 ID、标签或 Agent ID 找目标。
- **发送前五项检查**：目标不是线程子会话、所有权、可见性、双向通信白名单（A 能发 B 且 B 能发 A 才放行）、会话代次（防止发给已重建的旧会话）。
- **防死循环**：等待回复模式下禁止发给自己；来回对话设轮数上限（参考：5 轮）；配合 SKILL.md §5.2 的循环检测。
- **跳过标记**：用固定标记（如 REPLY_SKIP、NO_REPLY）表示“不需要回复/不要转发”，去掉首尾空白后**精确匹配**，不做模糊匹配，否则正文里提到这个词就会误触发。

## 并发底座

多 Agent 的很多 bug 其实是并发问题。用“车道”（lane）思路管理：
- **同一会话独占车道（宽度 1）**：同一会话的回合串行执行，避免两条消息同时改同一份上下文。
- **按类型分车道**：主会话、子 Agent、定时任务、嵌套调用各自限流（参考：主会话 min(16, max(8, CPU 核数))，其余各 8）。
- **为关键路径预留名额**：容量组里给钩子、审批等关键操作留位，避免被普通任务占满后卡死。
- **计数从活跃集合推导**：当前并发数由“正在运行的任务集合”实时算出，不维护手工加减的计数器（异常路径必漏减）。
- **互相等待的车道不能共享预算**：父在等子、子占不到名额 → 死锁。写成断言，启动时检查。
- **动态车道自动回收**：为单个会话临时建的车道，空闲后释放。
- **顺序**：先定车道契约（谁能并发、谁必须串行），再调参数，最后才考虑上中心协调器。

## 提示层

- **标注所有非用户文本的来源**：子 Agent 结果、工具返回、其他 Agent 的消息都要带来源标签。
- **子 Agent 的输出是证据或报告，不是指令**：不能覆盖父的策略和权限。被注入的子 Agent 会把恶意指令写进“结论”，见 SKILL.md §10。
- **委派偏好只是建议**：提示词里“优先委派/建议委派”这类设置影响模型倾向，不构成权限，权限只在代码层。
- **保护前缀缓存**：会话 ID、请求方等高基数值不要直接写进系统提示词，用占位符（如 `<REQUESTER_SESSION>`），在消息层再替换，否则每个会话一个前缀，缓存全部失效。

## 结果冲突与评测

- **子结果冲突时**：父 Agent 回到证据核实（原文、日志、工具返回），不按多数票裁决；无法判定时把分歧和各自依据如实交给用户，不强行合成一个结论。
- **评测**：评最终结果，也评过程（派生次数、深度、重复劳动、无效等待、总 token）；对子 Agent 的结论抽样独立复核；同任务多跑几次看方差，多 Agent 的方差通常比单 Agent 大。
- **对照基线**：同一批任务和单 Agent（或固定 workflow）对比，收益抵不过成本和不确定性就退回去。
