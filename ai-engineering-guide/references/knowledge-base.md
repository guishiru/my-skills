# 知识库 / RAG（详版）

适用：设计、评审、排查知识库与 RAG 方案时读本文件。章节编号与 SKILL.md §4 一致。

**核心判断**：知识库的准确率上限，在知识被写成什么形状时就定了。切分、检索、重排、提示词都只能在这个上限之下优化，救不回一条本身没写清楚的知识。所以顺序是：先治理知识，再调算法。

三条贯穿全节的原则：
1. **能在上游解决的不留给下游**：知识在后台本来就是结构化的就别再解析；元数据在写入时打好，检索时才能硬过滤；相似问在运营阶段写全。
2. **不让任何单一信号独占决定权**：向量和关键词互相印证；重排结果和重排前的排序再融合；模型自标引用和相似度回标互为兜底。
3. **能用规则算准的不交给模型**：数值由规则引擎或接口算，模型只组织语言；评测指标尽量做成编号比对和数值配对。

### 4.1 先判断：要不要建知识库检索

- 知识量小（几万到十几万 token）、更新不频繁 → 直接放进上下文 + prompt caching。
- 结构化数据（订单、库存、价格、活动规则、券规则、运费规则）→ 不走向量检索。几百到几千条的规则可全量载入内存用代码过滤，逻辑可读可测；数据库只负责存储和版本。
- 需要计算、组合推理或资格判定的问题（“再买多少能凑满减”“这单能不能退”）→ 知识库里只有原料或判断条件，没有答案。在意图路由阶段分流到规则引擎、业务接口或人工。
- 代码库、文件库 → Agent 自己用 grep / glob / 读文件搜索，往往比向量库更准、更易维护。
- 问题多半针对单个实体（某商品、某合同）→ 先按 ID 或名称定位实体，再把该实体的完整文档放进上下文，往往优于切块检索。
- 大量非结构化文档、语义提问、长尾问题 → 建检索。

### 4.2 知识形态与治理

**评价知识形态的四个标准**：
- **边界明确**：一眼看出一个知识单元从哪开始到哪结束。边界模糊的内容，用什么切分算法都是碰运气。
- **单独可读**：一个单元被单独取出来能读懂。检索命中是随机的，依赖前文才能理解的块在检索场景下等于无效。
- **可过滤**：时效、渠道、适用范围等有结构化字段，能做硬条件筛选，不靠语义相似度区分。
- **答案唯一**：同一问题只有一种口径。多口径时命中哪条答哪条，算法层无解，只能靠治理。

**值得投入的四种形态**（按优先级）：

| 形态 | 结构 | 适用内容 | 要点 |
|---|---|---|---|
| 问答对 | 标准问 + 相似问 + 答案 + 适用条件 | 高频、有标准答案、不随场景变 | 四条标准全满足，命中后可直接返回审核过的答案。**相似问从客服日志里挖，每个标准问配 5–10 条**，对召回率的提升通常超过调任何检索参数。只是精确层，覆盖不了长尾和多条件组合 |
| 关系型记录 | 一行一条，字段固定 | 活动、券、运费、参数配置 | 字段天然可过滤，改一个字段只影响一条；优先用程序处理（见 4.1） |
| 条款式规则 | 编号 + 层级 | 会员权益、售后政策、平台规则 | 编号即结构，可自动建层级树、溯源到“依据 3.1.1 条”。前提是同一文档编号体系统一 |
| 层级标题文档 | 严格分级，一节一事 | 操作指引、流程说明 | 一个小节只讲一件事，控制在三五百字；标题切得够细，切分就几乎无事可做 |

**难处理的形态与对策**：

| 层级 | 情况 | 对策 |
|---|---|---|
| 解析难（内容在但读不准） | 扫描件、图片型 PDF | 光学识别在表格、水印、低分辨率下错误率高，“满 300”可能读成“满 800”且下游无法发现。**涉及金额的识别结果必须人工复核** |
| | 多栏、跨页表格的 PDF | 阅读顺序会乱，跨页表格丢表头。能拿到原始文档就别用 PDF |
| | 演示文稿、流程图 | 信息在版面关系里（箭头、并列、颜色），抽成文本后丢失。人工或让模型逐页改写成完整句子；流程图改写成“第一步……如果……则……” |
| 切分难（读得出但找不到边界） | 会议纪要、通知、聊天记录、公众号文章 | 不要想办法切好，用模型抽取成结构化条目再入库：抽取比切分可控、也更容易验证 |
| | 报表型 Excel（合并单元格、多级表头、小计行） | 让运营按“一行一条记录”重填，或写脚本还原成规范表；前者更可持续 |
| | 几万字只有三个一级标题的手册 | 拆成多个文档，或强制补二三级标题 |
| 本质难（不是格式问题） | 需要计算或组合推理 | 分流到规则引擎（见 4.1） |
| | 需要跨多份知识组合（会员权益 × 区域 × 品类 × 渠道） | 优先把高频组合预先写成一条问答；多跳检索成本和延迟都高，是次选 |
| | 同一问题有多个时间版本（大促期和日常答案不同） | 文本极相似、向量分不开，必须靠**生效期字段硬过滤** |
| | 口径冲突（售后文档、活动页、客服话术说法不一） | 技术解决不了：确立唯一口径来源和责任人。系统只做冲突检测（同类目下语义高度相似但答案不同的条目对），消解靠人 |
| | 答案取决于个人状态（订单、商品类型、时间） | 查接口或转人工，硬答就是客诉 |

### 4.3 元数据

- **硬过滤**：生效期、状态、渠道作为硬条件下推给检索引擎，近邻搜索时只在满足条件的记录里找。活动一过期，相关内容自动从结果里消失，不用人工删索引。
- **在相似记录中提高区分度**：五十个活动的块结构相同、只有值不同，向量排序近乎随机；先用元数据砍到三条再排序。
- **版本共存**：同一条知识多版本共存于索引，用状态字段标识生效版本；回滚只改字段，秒级完成，不用重新切分和向量化。代价是存储翻倍。
- **溯源**：条目编号 + 来源字段，对外能说“依据活动规则第 3.1 条”，对内能定位是哪条写错、谁负责。
- **增量更新**：按内容哈希决定是否重算向量。只改了失效时间、正文没动，就只更新元数据，不重算向量。
- **权限**：不同角色可见范围用元数据过滤，不维护多套索引；权限过滤必须在检索层做，不靠提示词。

### 4.4 切分

目标只有一个：每一刀落在语义完整的地方，块既小到便于检索，又完整到能回答。

- **分隔符按优先级逐级降级**：标题 → 空行 → 换行 → 句号/感叹号 → 分号 → 逗号；代码块和表格整体保留。先按大边界切，切不动再降级，不按字数硬砍。
- **单段超限不硬切**：一个段落本身超预算时整体成块；从中间劈开会得到两个都读不懂的半截。但要设硬上限（如预算的 2 倍），超过才强制按句号切。
- **合并允许越界一次**：判断条件写成“当前累计是否已超”，而不是“加上下一段会不会超”，避免产生大量两三百字的碎块。
- **父子分段**：只对小的子块做向量化，命中子块后把所属父块全文放进上下文。子块语义集中好检索，父块上下文完整，例外条款（“商品质量问题除外”）不会丢。
- **补上下文**：合并或切出的块要带上标题路径（“第三章 优惠券使用规则 / 3.1 叠加规则”）；更进一步，可给每块加一句说明它出自哪篇文档、哪个部分的前缀再索引（上下文化切块），显著降低检索失败率。

### 4.5 索引选型

一个知识库要同时做三件事：向量检索（语义相近）、全文检索（关键词精确匹配）、结构化存储与过滤。规模按切分后的块数计，不是知识条数。

| 规模 | 方案 | 理由 | 代价 |
|---|---|---|---|
| 一万块以内 | PostgreSQL + pgvector + 中文全文扩展（如 pg_bigm） | 一条 SQL 同时完成过滤和排序；一套备份、一套监控；向量、全文、业务表同库，不用跨系统回查 | 向量数到几十万后延迟上升 |
| 中等规模 | 带原生 BM25 的向量库，或 ES + 独立向量库 | 前者一套引擎两路召回；后者两项能力都更强 | 多一套系统运维，跨系统一致性自己保证 |
| 五十万块以上 | 分离部署 + 按业务维度分片 + 冷热分层 | 全文吃磁盘、向量吃内存，分开避免抢资源；问活动只查活动分片；已结束活动移到冷存储但不删，问起来能答“该活动已于某日结束” | 架构复杂度上升 |

**升级看信号，不看数据量**：P95 延迟超过约 500 毫秒、索引重建时间影响知识更新时效、内存装不下向量索引、检索成为链路瓶颈。信号出现前，精力放在知识治理和评测上收益更大。检索层对外暴露统一接口，迁移就不痛苦。

**嵌入模型**：优先选可自托管的开放权重模型并记录版本，厂商下线时才不必全量重新嵌入。

### 4.6 查询改写与扩展

- **从问题里抽取过滤条件**：模型对照元数据字段清单输出结构化过滤条件。风险是静默失败（抽错条件，正确答案被筛掉），所以**生效期、发布状态等关键字段由代码强制注入**，模型只负责确实需要理解自然语言的部分。
- **指代消解**：把“那它能叠加吗”补全成独立问题。只喂最近两轮历史；改写结果和原问题一起检索，不替换。
- **相对时间归一化**：在提示词里先算好今天、昨天、明天的具体日期，示例答案里也写具体日期；按业务补上本周起止、当前进行中的活动名。
- **关键词补充**：让模型提取最重要的几个词拼到原问题后面。它解决不了用户说法和知识库说法不一致的问题（“满减没生效”vs“优惠未生效”），这要靠自建同义词表。
- **多查询扩展**：让模型生成约 10 条候选，再用向量按“与原问题相似（防跑偏）+ 与已选的不相似（防重复）”挑 3 条，每挑一条重算剩余分数。模型自己一次给几条，往往是同一句话的不同说法。这个方法也适合从客服日志里挑代表性相似问。HyDE（先生成假设答案再检索）是另一种扩展方式。
- **工程细节**：扩展是追加不是替换，原问题永远在第一位；重排时输入原问题和扩展查询的拼接；去重前先去掉标点空格；给改写器配一段业务黑话说明（“膨胀金”“黑卡”“百亿补贴”）；知识库不是多语言时不要做翻译改写，只会引入噪声。

### 4.7 混合检索与融合

- **两种融合方式**：加权求和能利用分数信息，但要求各路分数量纲接近；名次融合（RRF，常数常取 60）只看各路名次，跨路可比，多路来源异构时更稳妥，真正要调的是各路的权重系数。中文场景的专有名词、型号、金额、政策术语向量往往捕捉不准，关键词路通常要给较高权重（参考值：关键词 0.7 / 向量 0.3，需用自己的评测集验证）。
- **多路命中要加分，不取最大值**：同一块在两路都命中，说明语义和字面都对得上，应该排在只在一路命中的块前面。
- **融合分层**：先在同一来源内部融合，再合并不同来源；一次把四五路全扔进同一个融合，权重关系无法解释也无法单独调。重排只作用于它训练过的信号类型。
- **空路保护**：某一路没召回时不能继续占权重，否则会把其他路按比例稀释；这种 bug 不报错。
- **候选多取再收窄**：混合模式各路取的候选总数应多于单路模式（参考：向量 80 + 关键词 60）；漏取的结果再也没机会进入最终列表，多取只多算几十条排序。
- **处理顺序**：先去重，再按阈值筛，最后按长度预算截断；否则同一块会在阈值和预算里重复占位。
- **阈值只对同量纲的分数有意义**：为余弦相似度设计的阈值不能套在关键词分或融合分上，会静默误伤召回。任何阈值过滤前，先确认分数和阈值是同一种东西。
- **重排结果再融合一次**：重排模型在冷门查询、专有名词、业务黑话上打分不稳。重排后和重排前的排序各占一半再融合，除非明确要完全信任重排。
- **自研关键词检索时**：词权重在 IDF 之外乘上实体类型和词性系数（名词、地名、时间加权，代词、连词、副词降权）；电商新词（“满减券”“膨胀金”）词典里没有，要有未登录词的稀有度兜底；字段权重按可信度分阶梯（人工标注关键词 > 问答对的问题字段 > 标题 > 正文），同义词扩展、细分词匹配打折。用现成引擎时，这些多半是配置项。
- **Agentic RAG**：把检索做成工具，让模型决定检索什么、检索几次，适合探索性、多步的问题；代价是延迟和成本更高、结果更不可控，客服这类高频问答仍以固定链路为主。
- **GraphRAG / 知识图谱**：适合多跳关系、全局总结类问题；建图和维护成本高，先确认预写组合问答和元数据过滤解决不了再上。

### 4.8 生成、拒答与校验

**入口分流先于检索**（能确定答案的路径分走越多，整体准确率越高）：
- 标准问精确匹配（归一化字符串做键）→ 直接返回审核过的答案。它的主要价值是准确率而不是提速，应放在入口而不是链路末尾。
- 话里带订单号、“我的”“这单” → 答案在业务系统里，转接口。
- “你好”“谢谢” → 话术直接回复。
- 每次命中都记录用户实际问法，这是挖相似问最好的来源。

**提示词约束**：资料放 `<documents>` 标签内，要求引用出处、资料不足时明说。资料可能有误时，不要一刀切要求“只信文档”，让模型在资料与常识冲突时指出冲突。

**拒答三层**：
1. 硬拒答：检索结果为空（多半是元数据过滤后为空，如活动都已过期）→ 直接返回固定话术，不调用模型。
2. 阈值拒答：有召回但分数全部低于可用标准 → 不进入生成。
3. 软拒答：召回了、分数也够，但内容和问题不相关 → 只能靠模型在生成时识别，要求它输出固定拒答语。模型常会用不相关内容硬凑，所以软拒答不能单独依赖。

**按问题类型决定校验强度**（由意图路由的代码决定，不让模型自己判断要不要拆解）：
- 简单事实查询：直接生成，不做充分性判断。
- 计算、组合、资格判定：拆解子问题 → 逐个回答 → 下结论；数值由规则引擎或接口给，作为独立字段传入，提示词要求原样使用、不得推算或四舍五入。
- 高风险（金额、退款、赔付）：再加两道生成后校验。**数值回查**：正则抽出答案里的金额、折扣、日期、件数，逐个在召回原文中查找，有一个查不到就不返回。**实体回查**：用业务实体词典检查答案里的活动名、券名、渠道名是否都在原文中，拦截张冠李戴。两者都是几毫秒、零模型成本。

**置信度分三档**：高 → 直接回答；中 → 回答并提示“仅供参考，可转人工”；低或校验不通过 → 不生成，给转人工入口。用户连续两次点踩自动转人工。

**引用溯源两级**：
- 首选模型自标。提示词明确该引什么（数据、时间、因果、比较、定义、直接引述）、不该引什么（常识、过渡句、模型自己的归纳），每句最多若干个引用；解析前先修复格式（中文括号、缺冒号、一个括号塞多个编号）。
- 模型没标时才用相似度回标：答案按句拆，逐句与召回块算相似度，取接近最高分的块；整段都没匹配上就逐轮降低阈值再试。回标只代表“像”，不代表数字来自那个块，所以回标的引用要内部打标记并额外做数值回查；回标命中率太低时不显示引用，改为“本回答综合了知识库多条内容”。

### 4.9 缓存

- **标准问精确缓存**：见 4.8 入口分流。
- **语义缓存**：检索负责找候选，判定负责决定命不命中，两件事必须分开——找候选要宽，判等价要严。判定按成本从低到高三层：去标点后字符串相同直接命中 → 统一映射后的检索距离（换索引类型时阈值含义会变且不报错）→ 交叉编码器（能区分否定词、数量词、关键实体的差异）。
- **前缀缓存**：只省首字延迟。固定部分逐字不变放最前，检索结果和用户问题放最后；不要把当前时间、会话 ID 拼在开头，也不要每次动态调整示例。

### 4.10 评测与迭代闭环

**样本字段**（字段定好，多数指标就能自动算）：问法、问法风格（标准/口语/错别字/短问）、期望意图、应命中的知识块 ID、答案必含要点（3–5 条）、关键数值及其归属（如“满减门槛 199，归属双十一”）、应生效的过滤条件、是否应拒答、参考答案、样本有效期。

**四层指标**：
- 检索层：Recall@k（第一指标，零成本）、要点级召回（块召回了不代表要点在里面，用来区分“检索没给”和“给了没用”）、MRR/NDCG、**过滤准确率**（最容易静默失败）。
- 生成层：答案正确率（要点全中才算对）、**数值准确率**（规则比对）、**张冠李戴率**（比对“数值与活动名的配对关系”，忠实度类指标抓不到）、幻觉率、拒答准确率（该拒没拒、不该拒乱拒分开统计）、引用正确率；单独统计“被检索资料带错”的比例。
- 路由层：意图分类准确率（含多轮稳定性）、工具调用准确率、分流命中率。
- 业务层：会话解决率、转人工率、点踩率、响应时间、缓存命中率。业务层只用来报警，变差时回到前三层找原因。

**评测集来源**：
- 自动出题：生成问题、参考答案和来源块编号（期望知识块 ID 是免费副产品），人只做审核修正。按用户类型（新客、老客、会员）、提问风格、问题长度注入多样性，避免全是标准问法导致召回率虚高。
- 三类必须手工造：应拒答的题、时效性题、干扰题（两个相似活动的混淆场景）。数量不多，对应的却是最关键的三个指标。

**发布前回归闸门**：
- 知识改动、切分参数、召回权重、模型版本，任何变更都要触发。**知识变更不走代码发布流程，最容易漏掉闸门。**
- 核心指标要做到零成本可算（编号比对、要点命中、数值配对），全量跑几秒出结果；依赖模型判分的闸门迟早被绕过。
- 判定用“与上一版本逐指标对比”，不用绝对阈值；核心指标下降超过约 2 个百分点就阻断，并输出差异报告：哪些样本从对变错，附两个版本的召回列表和分数。
- 通过后先小流量灰度观察，再全量。

**上线后 bad case 闭环**：
- 入池信号：点踩、转人工、**连续换说法追问同一问题**（隐式但更有价值）。
- 入池时带完整链路快照：原问题、改写后的问题、召回列表及分数、最终答案。
- 归因用固定六类标签：内容缺失、切分问题、召回失败、排序错、生成幻觉、路由错。按标签分给知识运营、算法、工程。
- **修复后的样本必须加进评测集**，否则同一问题会换个形式再出现。
