# 长期记忆（详版）

适用：设计、评审、排查 Agent 长期记忆（跨会话记住用户偏好、事实、经历）时读本文件。

**来源与用法**：本文规则来自对 Letta（letta-code @271f119d，2026-10-10）、mem0（@b7ad69af，2026-10-07）、OpenClaw（@56812391894，2026-10-11）的源码研读确认版，并经独立审读筛过。每条标了共识度：

- **多家一致**：定位相同的项目做法一致（mem0 是库，很多事交给调用方，记为「不适用」，不算反对）。只有两三家，不等于「主流」。
- **参考 X**：只有一家这样做，按项目定位判断能不能照搬。
- **（推断）**：作者没说，从代码或现象推出来的。

文中数字都是**项目的参考值，没有校准依据**的会写明；不要当成定律，按自己的负载实测。用现成记忆框架时，把本文当评估清单，逐条问「框架怎么处理这件事」。

## 0. 先判断：要不要进长期记忆

| 信息 | 放哪里 |
|---|---|
| 只在本次会话里用到 | 上下文工程（会话历史 + 剪枝/压缩） |
| 业务系统里本来就有（订单、车型、会员等级、保养记录） | 查接口，不进记忆（业务承诺也以业务系统为准——作者方案，非研读结论） |
| 对所有用户都一样的资料 | 知识库 |
| 能从历史记录或文件里重新得到 | 不进记忆（Letta 提示词要求） |
| **只能从对话里得到、换个会话还要用** | 长期记忆 |

mem0 文档的说法：「只存以后值得复用的信息」。

记忆按类型分开设计，下面各节的做法都按类型区分：

| 类型 | 例子 | 怎么用 |
|---|---|---|
| 常驻的偏好、指令、用户画像 | 只用某品牌机油、回复要简短 | 每次调用都自动放进上下文 |
| 精选长期事实 | 用户的车、家庭情况 | 常驻或按需检索 |
| 日志、对话、事件 | 2026-10 换了四条轮胎 | 按需检索 |

## 1. 写入时机：提炼放在回复路径之外

**规则（多家一致：Letta、OpenClaw；mem0 不适用）**：回合内只便宜地追加原始材料（本地文件或表，不调模型）；把「提炼进长期记忆」交给后台流程，在回复用户之外完成。

- 触发点：「压缩之后」或「自上次**成功**提炼以来满 N 步」（Letta 默认压缩后；N 的参考值 25，没有作者理由）。
- Letta 专门把提炼从回合开始前挪到回合结束后，理由原话：「把读取对话记录和记忆快照，移出发送消息的关键路径」。
- **不这样会怎样**：每次回复都要多等一次模型调用；提炼失败直接挡住回复。

**游标规则（参考 Letta，不是共识）**：
- 游标（记录「原始材料处理到哪一条」）只在提炼结果真正落盘后推进；留下未提交改动、子 Agent 失败、合并冲突都不推进，下次原样重来。
- 只推进到**启动时**的位置，提炼期间新增的对话留给下一次。
- 以存储层的事实（合并结果）判断成败，不以子 Agent 自己报的成功为准（Letta 有测试专门验证）。
- 反例：Letta 旧版在任务开始前就推进游标，任务失败后那段对话永远不会再被处理。
- OpenClaw 只做到一部分：成功才写「已保存」标记，但失败 3 次后会强制标为已保存。

**例外**：
- 用户明确说「记住这个」：直接在前台写，并当场确认。
- 必须在回复路径上同步写（如 OpenClaw 压缩前保存）：把这一步收窄（只追加、每个压缩周期最多一次），并设失败上限（见第 2 节）。

**踩坑**：
- 两种触发条件（按 token、按文件大小）各自判断「本周期已保存」，其中一条绕过了检查 → 每条消息都触发保存。触发条件要共用同一个去重检查。
- 已有提炼在跑时新触发被直接丢弃，而「发生过压缩」的标记已被清除 → 这次提炼永远不来。保留一个排队的触发，出队时重新判断条件。

## 2. 失败可见：不让「没存上」冒充「存上了」

**规则（多家一致：三家都在真实故障或设计里显式防护）**：

1. **写入结果分四类返回**：调用失败 / 没内容可存 / 部分落库 / 全部落库。全部失败抛错；部分失败带上被拒的数量。
   - 依据：mem0 两次故障——模型调用失败静默返回空列表，上层分不清「模型不可用」和「没抽到事实」；批量写入部分失败仍向调用方报告「已新增」。修复注释原话：「被存储拒绝的记录，绝不能报告成新增成功。」
   - 反例（截至快照未修）：mem0 解析失败、向量化全部失败都返回空列表，等同「没东西可存」。
2. **自动重试用指数退避，同类失败只通知一次，配置类错误单独暂停**（参考 Letta：60 秒起、最长 30 分钟；为什么退避有说明——失败后立即重跑、重复告警，具体数值没有校准依据）。
3. **必须同步做的写入设失败上限，到上限后放行**（参考 OpenClaw：连续失败 3 次；为什么放行有说明，为什么是 3 没有）。
   - 依据：保存过程中模型服务崩溃，此后每条消息都卡在这一步。问题单原话：「当模型服务本身坏了，重试没有用。」
   - 放行时应默认告诉用户这一轮没存上。OpenClaw 准备了提示文案，但受一个默认关闭的开关控制，用户默认看不到——不值得学（作者意见）。
4. **后台汇总没有产出就升级告警**，不要每次写同一句「完成」。OpenClaw 注释原话：「无论成功还是全部失败，汇总都读起来一模一样，坏掉的流程就是这样一直没人发现的。」
5. **写入工具不可用时要有记录**：OpenClaw 写入工具被权限策略删掉时打警告，注释写明不打的后果：「模型报告已保存，而记忆丢了，且没有任何记录。」
6. Letta 提示词原话：「没有提交的编辑，不算记忆持久化成功。」

**常见静默失败点（评审时逐个问）**：
- 原始对话追加失败只写调试日志 → 那一回合永远不进入提炼（Letta）。
- 「哪些记忆被检索用到」的记录写入异常被吞掉，而后台升格正靠这些记录做决定（OpenClaw）。
- 退避状态只存在内存里，重启就清零（Letta）。
- 后台记忆维护失败不通知任何人（Letta 有意为之；业务系统至少要进监控）。

## 3. 常驻上限：设字符硬上限，写入时和注入时都设防

**规则（多家一致：Letta、OpenClaw 都设字符硬上限；mem0 不适用，没有常驻层）**。注意两家**口径不同**，不能直接比数字：

| | Letta | OpenClaw |
|---|---|---|
| 限什么 | 只限记忆本身（根目录 Markdown 文件合计） | 规则、身份、用户画像、记忆在内的全部启动文件合计 |
| 上限 | 65536 字符；单文件 20000 | 合计 60000 字符；单文件 20000；用户画像 `USER.md` 4000 |
| 检查点 | 写入时：提交钩子拒绝 + 推送前再审；注入时不截断 | 注入时截断副本，磁盘文件不动；另有后台写入预算 |
| 记忆的位置 | — | 排在最后，总量不够时最先被挤掉 |

**怎么定量级**：
- 参考 Letta：65536 字符，合并请求原话「对一般 Markdown 大约 1.6 万 token」（按英文）；Letta 初始化指南的经验值是「根目录保持在上下文窗口的约 10%」。
- 先定 token 预算，再按语言换算字符：英文约 4 字符折 1 token；中文一个字约 1–1.5 token，同样字符数在中文下 token 多得多。
- 多用户业务场景（每个用户一份画像）（作者判断，非研读结论）：画像通常远用不到窗口的 10%，可以参照 OpenClaw 给用户画像的固定小上限，按中文换算后实测。

**做法**：
1. 写清计数口径：字符还是 token、元信息算不算、哪些文件计入；警告阈值和硬上限用同一套口径。（反例：Letta 的「提示词过大」警告按「字节数 ÷ 4」估 token，中文一个字 3 字节，合规的中文记忆也可能触发（推断）。）
2. **注入时截断必须告诉模型**：OpenClaw 截断时保留开头 75%、结尾 25%，插入截断标记，并在系统提示里加「把项目上下文当作不完整的，细节缺失时直接去读文件」。
3. **后台写入预算低于注入上限**：OpenClaw 后台写 `MEMORY.md` 上限 10000 字符，刻意低于 20000 的注入上限，注释说是为了「让升格的内容始终能被看到」。写入预算超过注入上限 → 升格的内容注入时被截掉，模型看不到。
4. **不可分割的内容不截半**：OpenClaw 的用户画像超限就整份丢弃、退回默认，注释原话：「绝不能把一条被截断的指令变成新规则。」
5. **超限处理**：Letta 把非核心细节挪到索引后面（子目录只放一行索引，按需展开），不删除；后台自动整理要删旧条目时，设单次删除比例上限，删不下就推迟（OpenClaw：25%，没有校准依据；比例太小时旧条目 ≤3 条删 1 条就超限，整合退回追加——代码可推出）。
6. 把具体上限和超限处理写进系统提示（Letta 的 Agent 平时只知道「保持精简」，不知道具体上限）。
7. 上限的修改权归人，但写在配置里只防误操作；真要做安全边界，在服务端校验。

**不这样会怎样**：OpenClaw 早期后台升格只追加、写前不查大小，`MEMORY.md` 长到 50–100KB，有用户报告每回合输入涨到 10–19 万 token（问题单数字，未复核）。问题单评论原话：「注入时截断只保护每回合的注入成本，磁盘上的文件照样在长。」→ 只在注入时截断不够，写入侧也要有预算。

## 4. 去重：程序只做确定的事，语义判断交给模型

**现状（多家一致，限默认配置）**：三家代码都不判断「两条记忆是不是同一件事」。作者没说原因；可能的原因（推断）：向量阈值容易误伤（相似度 ≥0.95 就丢弃，只差一个数字的两条事实可能被吞掉），且删错比漏去重更难恢复。

**规则**：
1. **程序层拒绝逐字重放，并让模型重试，不要静默剔除**（参考 OpenClaw）：按段落或条目逐字比，规整只限换行、首尾空白和程序自己加的标注；命中就拒绝写入、文件不动，提示模型「只发新内容再试」。合并请求原话：「这是精确文本检测，不是语义去重。」
2. **防召回回灌**（参考 OpenClaw）：被检索注入过的内容做标记，不再被提炼。架构文档原话：「一个事实被召回一百次，也还是一个事实。」
3. **先查工具描述和实际行为是否一致**，这比加去重检查更根本。OpenClaw 的故障：保存工具实际只会追加，描述却写成覆盖写，模型交上整篇笔记被整篇追加，日志被重复内容撑大。
4. **改写或删除旧条目时，只让模型选择已有条目的编号，正文由程序拼出**；程序校验这些条目确实存在、只出现一次（参考 OpenClaw；模型编造编号曾让 mem0 旧版的更新删除失败、重复越积越多）。
5. **「检查 + 写入」串行执行**：mem0 两次并发写入各自基于旧快照检查通过、各自写入，产生永久重复（截至快照未修）。
6. **提示词里要求模型输出的字段，要么真的接上，要么删掉**。反例：mem0 提示词把「本会话最近抽取的记忆」称为「主要的去重参照」，调用时从不传入；要求矛盾时标出关联旧记忆，代码不读这一项。OpenClaw 文档说后台整合会「取代过时的事实」，「取代」依赖的字段在生产代码里从没被赋值。

**注意**：mem0 的指纹去重只和语义最相关的 10 条候选比、不做规整，候选外的逐字重复照样入库；换了说法的重复，逐字去重本来就拦不住。

## 5. 改写还是追加：按记忆类型选

| 记忆类型 | 做法 | 共识度 |
|---|---|---|
| 常驻的偏好、指令、用户画像 | **原地改写**，不追加矛盾条目 | 多家一致（Letta、OpenClaw；mem0 没有这一层） |
| 日志、对话、事件 | **只追加**，带日期 | 三家一致 |
| 精选事实层 | 分歧：Letta 改写，mem0 追加，OpenClaw「取代」在代码里走不通 | 分歧，按下面的条件选 |
| 用户要求遗忘的、敏感的、错误的 | **直接删除，不归档**，并清理所有副本 | 参考 Letta |

**为什么偏好要改写**：OpenClaw 原话：「偏好变了就改写这条指令，绝不追加一条矛盾的，因为只追加的偏好历史，会稳定地让模型按旧值回答。」Letta 规则最初的理由：「那样会留下两条互相冲突的记录。」

**改写时配三样防护**（OpenClaw 后台整合的做法）：可回滚的历史（或改写前保存原文）、单次删除比例上限、能唯一定位要改的那一条（模型只选编号）。旧条目标「已取代」留在旁边，或挪进**不进上下文**的归档区——注意归档区别放在常驻目录里（Letta 新版布局下归档文件可能常驻，推断）。

**追加的代价**：mem0 文档自己承认「知识更新仍是只追加架构最难的类别……语义相近的旧事实仍可能和新事实一起出现」；有未修问题单：用户换了公司，新旧两条并存、旧的排在前面。mem0 开源版排序没有时间信号，只靠提示词要求写清「从 A 变成 B」。mem0 转向追加的理由是「把能力花在理解输入上，而不是和已有状态做比对」，抽取延迟约减半；它的评测提升是一揽子改动的结果，**不能当作「追加更好」的证据**。

**精选事实层的选择条件（推断，作者归纳）**：
- **选改写**，满足任一：记忆会无条件进入上下文；是只有一个当前值的指令性状态；读取方拿不到可靠的时间信号。
- **选追加**，须同时满足：走检索、按需读取；排序有时间信号或把记录时间交给模型；新条目写清「从 A 变成 B」和绝对日期；有显式的修改和删除入口。
- 两条都不满足 → 名义上改写、实际上新旧事实并存，而且常驻。

## 6. 评测与合规（补充，非研读结论）

三家都没覆盖、但业务里要做的：

- **评测至少三件事**：该记的记住了没有；改过的偏好会不会被按旧值执行；不相关的记忆会不会被带进回答。
- **敏感信息**：Letta、mem0 写入路径不做内容级检测，只靠提示词或文档提醒；OpenClaw 只在摄入会话记录时做凭据类脱敏。面向大量用户的业务，手机号、车牌等在写入前脱敏。
- **多用户合规**：保存期限、删除权、删除是否覆盖记忆表、历史表、原始对话和备份。三家都是单主人或库的视角。
- **中文与成本**：分词、实体抽取、提示词示例以英文为主，中文效果要实测；每次后台提炼都调模型，用户量大时要估预算。

## 7. 排查（症状 → 先查什么）

| 症状 | 排查顺序 |
|---|---|
| 说了「记住」下次却不知道 | ① 写入结果是哪一类（调用失败 / 没内容 / 部分落库）② 原始材料追加有没有失败 ③ 提炼触发是否被跳过或吞掉 ④ 游标是否在失败时也推进了 ⑤ 常驻内容是否被总量上限挤掉或截断 ⑥ 写入工具在这个通道是否可用 |
| 按旧偏好回答 | ① 偏好是改写还是追加了矛盾条目 ② 「已取代」的旧条目是否仍在常驻区或检索结果里 ③ 检索排序有没有时间信号 ④ 新条目是否写清「从 A 变成 B」 |
| 记忆重复、越来越胖 | ① 工具描述和实际行为（追加 vs 覆盖）是否一致 ② 有没有逐字重放检查 ③ 召回内容是否被再次提炼 ④ 检查和写入是否并发 ⑤ 写入侧有没有预算（只在注入时截断挡不住磁盘增长） |
| 每回合 token 暴涨 | ① 常驻内容有没有硬上限、口径是否和语言匹配 ② 后台写入预算是否低于注入上限 ③ 归档区是否被误放进常驻 |
| 回复被记忆写入卡住 | ① 同步写入有没有失败上限和放行 ② 失败是否有退避 ③ 放行后是否告诉用户 |
